# 첫 Kendall 실행의 초기화 비용 분리

## 결론

Kendall 검정 엔진만 미리 생성하는 방식은 첫 분석을 포함한 총 대기 시간을 줄이지 못했다. 제품의 지연 생성 방식을 유지했다. 첫 호출 프로파일에서는 여러 함수의 첫 호출 컴파일 경로가 두드러졌다. 이번 작업에서 제품 코드는 변경하지 않았다.

## 측정

번들 Windows R 4.5.3, JIT 3, 영어 UTF-8, 패키지 검사 생략 및 기존 유효 모듈 캐시를 사용했다. 모듈 로딩 후 다음 세 방식을 각각 새 R 프로세스 세 개에서 순차 실행했다. 두 번째 회차는 일반/선생성 순서를 뒤집었다.

- 일반: 첫 분석에서 기존처럼 엔진을 지연 생성한다.
- 선생성: correlation_kendall_engine()을 먼저 호출하여 소요 시간을 따로 재고 첫 분석을 실행한다.
- 프로파일: 일반 실행의 첫 분석을 별도 Rprof로 관찰한다. 이 시간은 성능 판단 표에 합치지 않는다.

분석은 시드 33의 반올림 정규 자료 2,000행·6변수·15쌍, Kendall 지정, 정규성 및 잠재상관 비활성화 조건이다. 첫/두 번째 분석 시간에는 전체 결과 준비와 결과·진단·stdout·난수 수집이 포함된다. 엔진 준비와 첫 분석은 서로 겹치지 않는 단계이므로 두 시간의 합을 함께 기록했다.

| 방식 | 엔진 선생성 3회(초) | 첫 분석 3회(초) | 선생성+첫 분석 중앙값(초) | 두 번째 분석 중앙값(초) |
|---|---|---|---:|---:|
| 일반 | 해당 없음 | 0.27 / 0.25 / 0.27 | 0.27 | 0.05 |
| 선생성 | 0.00 / 0.02 / 0.00 | 0.27 / 0.27 / 0.25 | 0.27 | 0.05 |

선생성 후 전체 값은 0.27/0.29/0.25초였다. 엔진 생성 시간이 0으로 표시된 실행은 타이머 해상도에서 0이라는 뜻이다. 미리 생성한 시간을 누락하고 첫 분석만 비교해 개선으로 간주하지 않았다. 이 실험은 엔진 준비를 앞당기는 후보만 평가했으며, 모든 첫 호출 최적화가 효과 없다는 결론은 아니다.

## 첫 호출 프로파일

0.005초 간격 원시 스택을 확인했다. 세 실행 모두 전체 25개 표본 중 분석 run 프레임 아래 표본이 18개였고, 그중 compiler:::tryCmpfun을 포함한 표본이 16개였다. 엔진 생성 함수를 포함한 분석 표본은 0개였다. 표본이 없다는 사실은 엔진 생성 비용이 0이라는 뜻이 아니다.

프로파일이 system.time 호출 전체를 감쌌으므로, 시간 측정 시작 전 GC도 표본에 포함됐다. 분석 run 밖의 GC 표본 7/6/7개를 따로 분리했다. 따라서 전체 프로파일의 GC 비율을 첫 분석 경과 시간의 비용으로 해석하지 않았다. 컴파일 표본 역시 표본 기반 관측이며 경과 시간 0.27초 중 정확히 얼마를 차지한다는 의미가 아니다. 중첩된 컴파일 함수들의 누적 시간을 합산하지 않았다.

현재 근거는 엔진 사전 생성보다 실제 호출 함수들의 컴파일 경로가 후속 검토 대상임을 보여준다. 컴파일 정책 변경이나 시작 시 전체 함수 예열은 이번에 구현하지 않았다. 시작 단계로 비용을 이동시키기만 하는 변경은 총 대기 시간 개선으로 보지 않는다.

## 결과 보존과 범위

각 프로세스에서 첫/두 번째 결과가 정확히 같았고, 일반·선생성·프로파일을 포함한 9개 프로세스 간 전체 반환값·진단·stdout·난수 상태도 동일했다. 비교는 identical(..., num.eq=FALSE)이며 수치 정규화·반올림·허용오차를 사용하지 않았다.

프로그램 로딩·프로세스 시작·Shiny 서버 세션 초기화·UI·내보내기 시간은 이 실험에 포함하지 않는다. 이전 다른 프로세스의 로딩 시간과 합산하지 않았다.

`output/kendall-first-call-20260915/`에 measure.R, compare.R, 실행별 CSV/RDS, 원시 Rprof와 self/total CSV, timings.csv, profile-attribution.csv를 보존했다. 출력 변경이나 내보내기 생성·배포 빌드는 수행하지 않았다.
