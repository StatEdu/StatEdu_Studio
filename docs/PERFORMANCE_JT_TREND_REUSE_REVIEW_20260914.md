# JT 추세검정 결과 재사용 후보 검토

## 결정

추가 평균·표준편차 표에서 같은 추세검정이 두 번 실행되는 것을 확인하고 분석별 재사용을 구현해 검증했다. 수치와 진단은 일치했지만 최종 코드의 성능 이득이 일관되지 않아 이번 재사용 변경은 되돌렸다. 앞서 적용한 JT 비교 행렬 제거는 유지한다.

최종 프로그램 파일은 작업 전과 바이트까지 동일하다. `R/analysis_ttest_anova.R` SHA256: `BB7F3F0BA2058CEEFE03186436910EA1F36466854A8FB2B4EEF6190506A51EF4`.

## 후보와 정확성

기존 공통 캐시를 이용해 값·집단·정규성·등분산·순서형·강건 추세 옵션을 키로 저장했다. 실제 연결 후보는 비모수 분석에서 추가 표와 추세검정이 켜진 경우에만 재사용했다. 경고·메시지·난수 변경·오류가 발생하는 경로는 기존처럼 다시 실행하고 분석 호출마다 새 캐시를 생성했다. 최대 16개 항목 제한을 사용했다.

지역 범위로 함수를 연결한 예비 후보와, core/개별 결과 함수에 제공자를 전달하는 최종 연결 후보를 별도로 측정했다. 최종 연결 후보 검증은 다음과 같다.

- 전체 결과 36개: 2/4/8집단, 일반·동점·인접 실수·상수·결측·무한대, 추가 표 켜기/끄기, 종속변수 2개.
- 진단 주입 5개: 정상·경고·메시지·난수 변경·오류. 정상 경로의 호출은 2회에서 1회로 줄고 원시 JT 반환값도 기존 두 번의 결과와 정확히 일치했다. 다음 분석에서는 다시 계산했다. 나머지 경로의 호출 횟수와 관찰 결과는 기존과 같았다.
- 옵션 조합 16개: 정규성·등분산·순서형·강건 여부를 조합해 서로 다른 키와 반복 조회의 동일성을 확인했다.

모든 비교는 원시 반환값·진단·stdout·난수 상태를 `identical(..., num.eq=FALSE)`로 검사했으며 정규화나 허용오차는 사용하지 않았다.

## 최종 연결 후보 성능

20,000행, 2/4/8집단, 연속값/동점값, 결측률 0/0.1. 값과 집단에 독립적으로 결측을 적용했다. 순서형 집단에서 비모수·사후검정·추가 표·효과크기·추세검정을 켰다. 새 R 프로세스 3개에서 기존/후보를 예열한 뒤 순차 측정하고 두 번째 실행은 순서를 뒤집었다.

전체 분석과 결과·진단·stdout·난수 수집을 포함한 경과 시간이며 함수별 추적은 없다. 36개 최종 측정에서도 기존/후보 결과가 모두 일치했다. 대표적인 3회 중앙값은 다음과 같다.

| 집단 | 입력 | 결측률 | 기존(초) | 후보(초) |
|---:|---|---:|---:|---:|
| 2 | 동점값 | 0 | 0.06 | 0.07 |
| 4 | 연속값 | 0 | 0.17 | 0.16 |
| 4 | 동점값 | 0.1 | 0.05 | 0.06 |
| 8 | 연속값 | 0 | 0.21 | 0.19 |
| 8 | 연속값 | 0.1 | 0.17 | 0.16 |

8집단 연속값은 3회 모두 단축됐지만, 4집단·동점·결측 자료는 기존 0.06/0.05/0.05초에서 후보 0.05/0.07/0.06초로 3회 중 2회 증가했다. 작은 실행 시간은 해상도와 실행 변동의 영향을 받는다. 앞서 JT 계산 자체가 빨라진 상태에서, 이 추가 재사용의 이득만으로 제공자 전달과 캐시 유지보수 범위를 늘릴 근거가 충분하지 않다고 판단했다.

예비 후보의 8집단 연속값 중앙값 0.22→0.19초와 최종 연결 후보의 0.21→0.19초는 별도 측정이며 혼합하지 않는다.
