# Cox 다중공선성 진단의 유한값 행 검사 개선 — 2026-09-14

> 검증 범위 정정 (2026-09-14): 아래의 경쟁위험/Fine–Gray 전체 결과 검증 표현은 당시 `integration.R`이 `regression`을 지정하지 않아 기본 CIF/Gray 경로만 실행한 것을 잘못 기술한 것이다. 그 검증은 원인별 Cox 또는 Fine–Gray 회귀 검증으로 볼 수 없다. 직접 함수 및 Cox 검증 결과는 별개다. 이후 `regression="both"`를 명시한 600행·20공변량 자료에서 초기 Cox 최적화 전과 현재 모듈 전체의 결과·진단·난수 상태를 비교해 통과했다. 상세 내용은 [원인별 Cox 저장·통합 검증](COMPETING_PH_EXPORT_VALIDATION_20260914.md)을 참고한다.

`survival_cox_collinearity`에서 일반 행렬의 각 행에 R 함수를 호출하던 유한값 검사를 `rowSums(!is.finite(design)) == 0`으로 변경했다. 클래스가 있는 객체는 기존 apply 경로를 유지한다. 숫자 행렬 변환과 double 변환 이후에 적용하며, 결측·무한값이 있는 행을 제외하는 규칙은 같다. VIF 보조회귀, 분산, 조건수 및 판정 기준의 계산식과 순서는 변경하지 않았다.

이 함수는 Cox 및 Fine–Gray 진단에서 사용된다. 실행 코드에 적용했으며 이전 RMST 개선도 유지한다.

## 측정

번들 R 4.5.3, 앱 설정 적용, 자동 설치 비활성화. 새 프로세스에서 변경 전후 3쌍을 순차 실행했고 두 번째 쌍은 순서를 반대로 했다. 각 프로세스는 1,000행 다음 100,000행, 공변량 5개 숫자 자료를 실행했다. 대상 함수의 환경은 같은 전역 환경에 연결했다. 검증은 시간 측정과 동시에 실행하지 않았다.

| 행 수 | 변경 전 3회(초) | 변경 후 3회(초) | 중앙값 전→후 |
|---|---|---|---|
| 1,000 | 0.02 / 0.03 / 0.03 | 0.01 / 0.03 / 0.02 | 0.03→0.02 |
| 100,000 | 0.26 / 0.28 / 0.28 | 0.17 / 0.15 / 0.16 | 0.28→0.16 |

10만 행 조건에서 약 43% 감소했다. 작은 조건의 0.01초 차이는 실행시간이 짧고 범위가 겹치므로 뚜렷한 개선으로 주장하지 않는다. 시간은 다중공선성 진단 함수 전체이며 Cox/Fine–Gray 적합, 다른 진단, UI·내보내기·앱 로딩은 포함하지 않는다. 메모리 사용량은 별도로 측정하지 않았다.

## 검증

- 직접 입력 36조건에서 전체 결과·진단·난수 상태가 identical(..., num.eq=FALSE)로 일치했다. 빈/단일/2/40행, 결측, 무한값, 상수·동일 열, 행 이름, 데이터프레임, 단일 열, 특수 행렬 클래스를 포함했다.
- 시간 측정 6쌍에서도 전체 결과·진단·난수 상태가 정확히 일치했다.
- 실제 600행 자료의 Cox와 공변량을 포함한 경쟁위험/Fine–Gray 분석 및 두 HTML/의존성 객체를 비교했다. Fine–Gray 전체 결과·진단·난수 상태는 원본 그대로 정확히 일치했다.
- Cox 원본 객체의 identical 검사는 수식 실행 환경 참조 때문에 실패했다. 차이를 추적한 결과 fit$terms, fit$model의 terms, fit$formula, 최상위 formula의 `.Environment` 4곳이었다. 검증용 복사본에서 이 네 참조만 같은 환경으로 정규화한 뒤 전체 결과·진단·난수 상태가 정확히 일치했다. 숫자·표·수식 본문은 정규화하거나 허용오차를 적용하지 않았다. 이는 원본 Cox 객체의 바이트 단위 동일성을 주장하는 검사가 아니다.
- 초기 검증 자료 생성 시 빈 행렬에 행 이름을 지정하던 오류는 시험 코드에서 수정했다.
