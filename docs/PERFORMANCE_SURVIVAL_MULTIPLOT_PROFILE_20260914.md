# 생존분석 8개 그림 저장 경로 프로파일

2026-09-14. 운영 코드 변경 없이, 다중 그림 저장에서 반복되는 준비 작업과 고해상도 출력 비용을 구분했다.

## 조건

번들 R 4.5.3/JIT 3, 기존 모듈 표현식 캐시, 설치 검사 생략. seed 714로 만든 2,000행 자료(time 지수분포, 사건확률 0.65, 4개 그룹)를 KM으로 분석했다. 평가 시점은 5/10/20/40이다. 생존·사건·누적위험·로그생존 곡선을 컬러/흑백으로 각각 저장하여 총 8개 그림을 HTML에 포함했다.

분석 준비는 측정 밖에서 수행했다. 새 R 프로세스 3개에서 계측 없이 첫 저장과 반복 저장을 측정하고, 별도 새 프로세스 3개에서 같은 흐름에 helper 계측과 첫 저장 Rprof를 적용했다. 모든 프로세스는 순차 실행했다. Rprof 간격은 0.01초이고 system.time의 사전 GC 이후에 시작했다.

측정 스크립트의 예약어 필드 접근 문법 오류로 최초 시도 1개가 실패했다. 해당 접근을 수정한 후 최종 6개 프로세스를 모두 실행했으며, 실패 시도는 결과에 포함하지 않았다.

helper 시간은 하위 호출 및 지연 인수 평가를 포함하므로 행을 합산하지 않는다. 첫 두 행 외의 값은 계측 실행의 측정치다. 곡선용 데이터 준비와 추적기간 진단은 서로 별도의 호출 경로로 합계 약 0.06초이며, 캐시를 만들더라도 전체 저장 비용 중 작은 부분만 대상으로 한다.

HTML에서 8개 PNG를 추출하여 IHDR 크기를 확인했다. **모두 5455×3927픽셀**이다. 원래 표시 크기 1000×720, res 110을 현재 600 dpi 출력 설정에 맞춰 확대하는 기존 `plot_data_uri` 동작에 해당한다. PNG 한 개의 파일 크기는 약 189~265KB이지만, 래스터 작업은 각 2천만 픽셀 이상을 처리한다. 파일 크기만으로 출력 작업량을 판단하지 않는다.

## 표본 프로파일

첫 저장 Rprof 표본 시간은 약 7.9초로 실제 경과 시간보다 짧았다. 표본 안의 누적 비율은 다음과 같다.

- `grid.Call.graphics`: 32.74 / 33.63 / 33.08%
- `grDevices::dev.off`: 27.18 / 26.93 / 27.12%
- `survival_km_plot_data`: 0.25 / 0.38 / 0.13%

표본 비율을 전체 벽시계 시간의 정확한 분할로 해석하지 않는다. `dev.off`는 장치 종료와 PNG 저장 완료 작업을 포함하며, 위 수치가 순수 디스크 쓰기 시간만을 뜻하지 않는다. 높은 비중은 그래프 그리기와 장치 출력에 나타나며, 반복 데이터 준비는 작다.

## 보존 검증과 판단

6개 프로세스의 저장 HTML(내장 PNG 포함), 경고·메시지, 표준 출력, RNG 상태가 `identical(..., num.eq=FALSE)`로 모두 같았다. 각 프로세스의 첫/반복 저장도 같았고, 저장 전후 원래 분석 결과의 직렬화 바이트도 그대로였다.

이번 조건에서는 반복 준비 작업의 캐시를 추가하지 않는다. 다음 후보는 **동일 해상도·동일 픽셀을 보존하는 PNG 생성 및 저장 경로**다. 해상도를 낮추거나 곡선 데이터를 줄여 얻는 속도 개선은 이번 결과 보존 목표에 맞지 않는다. 다른 표본 크기에서 준비 비용의 비중은 달라질 수 있다.

측정 대상은 그림을 포함한 저장 HTML 생성이다. 실제 PDF/Word/HWPX 변환, Excel 작성, 프로그램 시작 또는 메모리 최고점은 측정하지 않았다. 운영 코드와 출력 내용은 변경하지 않았으며 전체 형식 내보내기 및 설치 파일 재빌드도 하지 않았다.
