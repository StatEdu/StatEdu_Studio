# 상관분석 저장 이미지 캐시 메모리 검토 — 2026-09-14

현재 적용된 이미지 캐시를 검토했다. 측정 범위에서 최대 메모리 증가나 반복 초기화 후 데이터 누적은 발견하지 않았다. 이번에는 제품 코드를 변경하지 않았다.

## 프로세스 최대 메모리

번들 R 4.5.3, Windows, 2,000행 × 8개 연속변수 Pearson 분석, 산점도 행렬과 열지도, 기본 600 dpi를 사용했다. 기존 `plot_data_uri`와 실제 `correlation_export_image_cache()`를 각각 새 R 프로세스 3개에서 실행했다. 프로세스마다 첫 HTML 생성과 반복 생성을 수행했으며, 두 번째 쌍은 실행 순서를 반대로 했다. 다른 R 검증과 겹치지 않게 실행했다.

실제 계산 R PID를 기록하고 Windows `PeakWorkingSet64`를 관측했다. 이 값은 패키지/모듈 로딩, 분석, 두 차례 HTML/PNG 생성 및 검증 자료 저장을 포함하는 프로세스 전체 최고치다. 캐시만의 메모리나 저장 구간만의 최고치가 아니다. MB는 1,000,000 bytes다.

| 회차 | 기존 방식 MB | 캐시 적용 MB |
|---|---:|---:|
| 1 | 419.914 | 407.491 |
| 2 | 419.824 | 407.593 |
| 3 | 419.811 | 407.605 |
| 중앙값 | 419.824 | 407.593 |

이 자료에서 중앙값은 12.231 MB(2.91%) 낮았다. 모든 자료나 장시간 세션에서 같은 차이가 난다는 의미는 아니다. 이번 실행 시간은 메모리 관측의 영향을 받으므로 속도 개선 수치로 사용하지 않는다.

## 결과와 캐시 수명 검증

- 3쌍 모두 HTML 전체(내장 PNG 포함), 경고/메시지, 표준 출력, 난수 상태가 `identical(..., num.eq=FALSE)`로 일치했다. 각 프로세스의 첫 생성과 반복 생성도 일치했으며 분석 결과 직렬화 값이 변하지 않았다.
- 실제 PNG 렌더러로 초기화 → 저장 → 반복 저장 → 초기화를 12회 수행했다. 각 회차에서 결과 객체에 고유한 검사 속성을 붙여 캐시 키를 바꿨다. 통계값 자체를 바꾸는 검사는 아니다.
- 매회 저장 후 항목은 정확히 2개였고 두 키 모두 그 회차의 결과와 일치했다. `object.size(entries)`는 2,681,736 bytes로 일정했다. 초기화 후 항목은 0개, 빈 리스트 추정 크기는 48 bytes였다.
- 측정 기록을 미리 할당한 행렬에 보관했다. 초기화 및 `gc()` 후 사용 중인 셀 수는 2~12회 모두 Ncells 1,743,496, Vcells 1,727,044로 일정했다. 이는 이 반복 검사에서 R 객체가 계속 누적되지 않았다는 근거이며 OS에 메모리가 즉시 반환된다는 증거는 아니다.
- 기존 `scripts/validate_correlation_export_image_cache.R`를 재실행해 정확한 키 비교, FIFO 2개 제한, 인자/함수/문맥 변경, 세션별 독립 객체, 초기화, 바이트 제한 우회, 경고/메시지/난수 변경/오류 시 캐시 우회를 확인했다.

16 MiB 제한은 보관 항목에 대한 `object.size` 추정치다. 프로세스 전체 메모리, 렌더링 중 일시 메모리, 환경이 참조하는 모든 객체의 재귀 합계를 제한하지 않는다. 실제 서버의 새 분석·초기화·세션 종료 연결과 5종 현재/누적 출력 검증은 직전 적용 보고서에 있으며, 이번에는 해당 소스 해시가 유지됨을 확인했다. 출력 코드 변경이 없어 파일 형식 변환은 재실행하지 않았다.
