# Gwet 범주 매칭 일괄 처리 검토: 미적용

## 결론

행마다 문자 변환과 match를 수행하는 대신 일반 문자 행렬 전체를 한 번에 범주 코드로 바꾸는 후보를 검토했다. 원시 결과 검증은 통과했으나 순서형 전체 분석에서 일관된 속도 개선이 없었고, 20,000행에서는 세 번 중 두 번 느려져 적용하지 않았다. 기존 쌍 인덱스 캐시와 다른 개선은 유지한다.

## 후보

interrater_row_frame 결과가 객체 클래스 없는 character matrix이고 levels도 일반 character 벡터인 경우에만 `matrix(match(row_frame, levels), ...)`를 생성한다. 행 루프에서는 해당 정수 코드 행을 읽고 기존 결측 코드 제거·빈도·쌍 가중치·누적 계산을 그대로 수행한다. 그 외에는 기존 행별 변환 경로를 유지한다. 숫자나 factor 변환의 의미를 바꾸는 후보는 아니다.

행렬 전체에 대한 정수 코드가 추가로 필요하다. 이번에 메모리 최고 사용량을 측정하지 않았으므로 메모리 개선이라고 주장하지 않는다.

## 성능

번들 R 4.5.3, 자료 seed 939, 8평가자, A–E와 NA를 같은 확률로 표집한 자료다. 명목형/순서형 전체 prepare_interrater_agreement_results를 비교했다. 5,000행 측정의 차이가 작고 불안정해 앞선 병목 측정과 같은 20,000행에서도 확인했다.

각 크기에서 독립 프로세스 3개를 순차 실행했다. 워밍업 후 두 번째는 후보부터 측정했다. 로딩을 제외하고 전체 결과 캡처를 포함한다.

| 행 수 | 유형 | 현재 1 / 2 / 3 (초) | 후보 1 / 2 / 3 (초) | 중앙값 |
|---|---|---|---|---|
| 5,000 | 명목형 | 0.20 / 0.11 / 0.19 | 0.12 / 0.19 / 0.10 | 0.19 → 0.12 |
| 5,000 | 순서형 | 0.08 / 0.08 / 0.08 | 0.09 / 0.08 / 0.08 | 0.08 → 0.08 |
| 20,000 | 명목형 | 0.42 / 0.38 / 0.41 | 0.39 / 0.39 / 0.37 | 0.41 → 0.39 |
| 20,000 | 순서형 | 0.29 / 0.36 / 0.28 | 0.36 / 0.25 / 0.36 | 0.29 → 0.36 |

20,000행 순서형은 두 번 느려졌고 중앙값도 증가했다. 명목형에서 관측된 개선을 무시하지 않지만 이 결과만으로 공통 계산 경로를 바꿀 근거가 충분하다고 판단하지 않았다. 전체 시간의 차이가 발생한 내부 원인까지 입증한 측정은 아니다.

## 검증

기존 Gwet 검증 스크립트를 후보 소스를 읽는 형태로 별도 복사하고 변경 직전 실제 소스를 참조로 지정했다. 평가자 수 1/2/3/10/30/32/33/40, 완전·결측·희소·미등록 값·빈·factor 자료, AC1/AC2 및 가중치 조합의 192개 원시 계수·조건·RNG 비교가 통과했다.

두 자료 크기의 전체 분석 측정 12건과 각각의 워밍업 비교에서 전체 반환 객체, 조건 클래스·본문·순서, 표준 출력 및 RNG가 `identical(..., num.eq=FALSE)`로 일치했다. 수치 허용오차나 정규화는 사용하지 않았다. 같은 자료 조건을 반복한 것이며 모든 사용자 클래스나 잘못된 levels의 동작을 검증한 것은 아니다.

## 증거 및 범위

제품 파일은 변경하지 않았으며 시작 스냅샷과 해시 일치를 확인했다. 출력 변경이 없어 전체 형식 변환·설치 파일 빌드·종합 일치도 검증은 재실행하지 않았다.
