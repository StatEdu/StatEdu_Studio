# 범주 라벨 입력 수집 검토: 후보 미적용

2026-09-15. `collect_category_label_inputs_from_table()`에서 각 입력 ID의 접두사를 한 번 만들고, 행마다 ID를 벡터로 생성하는 후보를 비교했다. `var_label` 분기는 일반 ID 조합과 같은 문자열을 생성하므로 후보에서 제거했다.

결과는 같았지만 실제 Shiny 입력 객체를 사용한 측정에서 일관된 속도 이득이 없었다. 제품 함수는 기존 코드로 복원했다. 다른 함수의 코드는 이 검토에서 변경하지 않았다. 복원한 함수 텍스트를 기준 fixture와 비교하고 다른 코드 구간도 후보 생성 당시와 동일함을 확인했다(줄바꿈 형식과 파일 끝 공백을 제외한 함수 텍스트 비교).

## 검증

- `scripts/validate_category_input_collect.R`: 일반 list, environment, Shiny reactiveValues에서 189개 반환값 전체/진단/stdout/RNG 정확 비교 통과. 0/1/12행, 1/3/11 범주 쌍, 일반 문자·NULL·다중 값·NA·list·factor·숫자 입력 포함.
- active binding으로 실제 입력 조회 순서를 기록하여 일반·중복·빈 값·NA·factor·특수문자 이름/순번 조건 6개 비교 통과.
- 화면의 입력 ID 생성 코드와 서버 호출 경로를 확인했다.
- 기존 스냅샷 처리 299개 비교를 재실행하여 통과했다.

## 측정과 판단

`scripts/benchmark_category_input_collect.R`에서 Shiny reactiveValues를 `isolate()` 안에서 읽었다. 두 함수를 동일하게 컴파일하고 사전 호출 후 순서를 교대했다. 독립 프로세스 3회, 조건별 3회 중앙값이며 모든 측정 반환값도 정확히 비교했다. `Sys.time()` 측정 구간에는 수집 함수와 isolate/진단 수집이 포함된다. 객체 생성 및 명시적인 GC는 측정 밖이다.

없는 입력은 두 실행에서 약 4% 느려졌고, 모두 있는 입력도 두 번째 실행에서 약 4% 느려졌다. 문자열 조합 변경만으로 안정적인 개선이 확인되지 않아 채택하지 않았다. 100행 조건도 CSV에 기록했다.

이 결과는 격리된 Shiny 객체의 대량 입력 수집 측정이며 실제 브라우저 저장 버튼 응답 시간, 파일 쓰기, 전체 로딩, 분석 계산 시간을 뜻하지 않는다. 대량 입력 수집 자체에 추가 조사 가치가 있으나 Shiny 내부 비용의 원인은 이번 측정만으로 확정할 수 없다.

후속 후보는 ID 조합의 미세 변경보다 입력 수집 횟수와 Shiny 조회 비용의 분리 측정이다. 의존성 및 이벤트 동작을 확인하기 전 일괄 조회로 교체하지 않는다.
