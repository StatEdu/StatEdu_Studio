# 빈도분석 다중 그림 저장 병목 검토 — 2026-09-14

빈도분석의 5개·20개 그림 저장을 측정했다. 반복 저장의 주된 비용은 PNG 생성이었다. 기존 상관/PCA/EFA의 2항목 이미지 캐시를 그대로 연결하면 재사용되지 않는 것을 확인했다. 이번에는 제품 코드를 변경하지 않았다.

## 방법

번들 R 4.5.3, Windows, seed 714, 2,000행 합성 자료를 사용했다. 범주변수는 4수준, 연속변수는 정규분포다. 범주변수마다 원·막대 그림, 연속변수마다 히스토그램·상자·바이올린 그림을 켰다. 작은 사례는 범주 1개·연속 1개(그림 5개), 큰 사례는 범주 4개·연속 4개(그림 20개)다.

각 사례를 새 프로세스 3개에서 첫·반복 저장했고 두 번째 회차는 사례 실행 순서를 반대로 했다. 별도 새 프로세스 1개씩에서 `Rprof(interval=.01)`와 그리기/PNG URI 구간을 계측했다. 모든 R 실행은 순차 수행했다. 패키지 로딩과 분석을 완료한 뒤 저장용 HTML 생성만 측정했으며 앱 시작·분석·대화상자·파일 형식 변환은 제외했다.

## 시간

| 그림 수 | 첫 저장 3회(초) | 반복 저장 3회(초) | 첫 중앙값 | 반복 중앙값 |
|---|---|---|---:|---:|
| 5 | 0.76 / 0.80 / 0.77 | 0.48 / 0.47 / 0.50 | 0.77초 | 0.48초 |
| 20 | 2.07 / 2.02 / 2.05 | 2.27 / 2.20 / 2.12 | 2.05초 | 2.20초 |

별도 계측 실행의 전체 시간은 5개 첫 0.79초·반복 0.49초, 20개 첫 2.08초·반복 2.08초였다.

| 계측 구간 | 5개 첫 / 반복 | 20개 첫 / 반복 |
|---|---:|---:|
| PNG URI 생성 합계 | 0.45 / 0.40초 | 1.70 / 1.97초 |
| 실제 그리기 함수 합계 | 0.08 / 0.05초 | 0.29 / 0.31초 |

그리기 시간은 PNG URI 생성 시간에 포함된다. 20개 반복 사례에서 URI 생성은 경과 시간의 약 94.7%였다. `Rprof`의 `grDevices::dev.off` 총 샘플 비중은 69.12%였다. 샘플 비중은 전체 경과 시간 비율과 구분해야 한다. 통계 요약 계산을 다시 최적화하는 것보다 반복 PNG 생성 제거가 우선 후보다.

## 크기

기본 600 dpi에서 그림마다 2,625×2,000 픽셀이다. 다음은 파일/객체 크기이며 프로세스 최고 메모리나 실제 공유 메모리 증가량을 측정한 값은 아니다.

| 그림 수 | PNG 원본 합계 | 분석 결과 `object.size` | HTML `object.size` |
|---|---:|---:|---:|
| 5 | 165,714 bytes | 42,496 bytes | 725,720 bytes |
| 20 | 656,605 bytes | 150,368 bytes | 1,460,592 bytes |

PNG 압축 파일은 작아도 픽셀 렌더링 비용은 크다. 여러 그림을 보관하는 캐시의 실제 메모리는 키·문맥·결과 보관까지 포함해 별도 검증해야 한다. 이 표만으로 필요한 캐시 크기나 프로세스 메모리를 단정하지 않는다.

## 기존 캐시를 그대로 적용할 수 없는 이유

`saved_frequency_plot_blocks`는 각 그림 호출마다 `function(plot_result) draw_frequency_plot(plot_result, type, name)`을 새로 만든다. 같은 변수·그림이라도 함수 환경이 달라 기존 캐시의 정확한 함수 비교에서 다른 키가 된다. 그림 1개를 두 번 만드는 모의 검사에서도 실제 렌더러 호출이 2회 발생해 재사용되지 않았다.

또한 기존 캐시의 보관 상한은 2개다. 함수 자체를 고정해도 5개·20개 그림을 같은 순서로 순회하면 뒤의 그림이 앞의 그림을 밀어낸다. 다음 순회 역시 모든 항목이 실패한다. 모의 렌더러로 기존 그림 블록과 고정 함수 두 경우를 검사한 결과, 반복 렌더 횟수는 각각 5회·20회로 감소하지 않았다. 이는 키와 보관 정책 검사이며 실제 PNG 속도 개선 실험은 아니다.

다음 구현 후보는 그림 종류·변수명·결과·표시 문맥을 명시적인 키로 삼고, 그림 수를 수용하면서 바이트 상한을 지키는 세션 캐시다. 실제 전체 저장 이득과 보관량, 자료·옵션 변경/초기화/세션 종료, 조건·RNG 및 5종 현재·누적 출력 동일성을 검증한 뒤 적용해야 한다. 이번 검토에서는 이를 구현하거나 속도 개선을 주장하지 않는다.

## 검증·재현

두 사례의 일반 실행 각 3개와 프로파일 실행 각 1개, 총 8개 프로세스의 HTML 전체(내장 PNG), 경고·메시지·표준 출력·RNG가 같은 사례 내에서 `identical(..., num.eq=FALSE)`로 일치했다. 각 실행의 첫·반복 출력도 같았고 분석 결과 직렬화 값이 변하지 않았다. PNG 개수와 치수도 확인했다.

제품 출력 변경이 없어 5종 파일 변환은 재실행하지 않았다. 설치 파일도 빌드하지 않았다.
