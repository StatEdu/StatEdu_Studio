# 범주 라벨 표의 저장값 조회 개선

## 적용

`R/data_category_labels.R`의 `category_label_display_data()`에서 저장된 열 이름의 존재 여부를 셀마다 반복 확인하지 않고 적용 가능한 열 목록을 한 번 만든다. 일반 문자형 변수 이름은 전체 match 결과를 한 번 계산한다. factor·숫자 등 다른 이름 자료형은 기존 행별 match 경로를 유지한다.

행 순서와 열 적용 순서, 중복 이름의 첫 일치 선택, 라벨의 문자형 변환 및 셀별 대입은 그대로다. 이름이나 라벨을 호출 사이에 보관하는 캐시는 없다. 분석 수식과 자료 선택 범위를 변경하지 않았다.

## 검증

변경 전 함수와 관련 열 이름 helper를 `scripts/fixtures/category_label_lookup_reference.R`에 보존했다. `scripts/validate_category_label_lookup.R`는 0/1/12/100행 × 저장값 없음/전체/일부/중복 이름/NA 이름과 값/factor/숫자 이름 × 1/3/11개 라벨 쌍의 84개 조건에서 전체 반환값·속성·진단·표준 출력·최종 RNG를 정확 비교한다. `identical(..., num.eq=FALSE)`가 모두 통과했다. 연속형 변수의 필터 제외와 역할 지정도 입력에 포함했다.

추가로 한국어와 영어의 범주 라벨 편집 표 HTML을 고정 elementId로 생성해 비교했다. 컬럼 정의·옵션·콜백을 포함한 두 HTML이 정확히 일치했다. 기존 `validate_data_io.R`도 통과했다. 실제 브라우저에서 라벨을 수정·저장하는 동작이나 내보내기 전 형식의 신규 검사는 이번 범위에 포함하지 않는다.

초기 연구 데이터 생성에서 paste0와 길이 0 벡터의 조합이 1개 문자열을 만들어 오류가 났다. 빈 행의 문자열 벡터를 명시적으로 비우도록 수정한 후 전체 비교와 측정을 수행했다. 이는 연구 fixture 오류이며 제품 결함이 아니다.

## 측정

번들 R 4.5.3의 독립 프로세스 3개에서 500/2,000개 변수 및 일부/전체 저장 열 조건을 각각 3회 비교했다. 후보와 기준 함수는 같은 바이트 컴파일 조건이며 실행 순서를 교대했다. 준비 호출 및 각 측정 결과도 기준과 비교했다. 시간은 표 데이터 준비와 진단 캡처까지 포함하며 HTML/브라우저는 포함하지 않는다.

|2,000개 변수 중앙값(초)|기존 1/2/3|개선 1/2/3|
|---|---|---|
|전체 라벨 열 저장|0.75 / 0.95 / 0.95|0.58 / 0.80 / 0.79|
|이름·reference만 저장|0.07 / 0.07 / 0.09|0.03 / 0.03 / 0.03|

전체 저장 조건은 약 16~23%, 일부 열 조건은 약 57~67% 감소했다. 프로세스 간 부하 변동이 있어 각 프로세스의 비교를 제시한다. 500개 변수의 작은 일부 열 조건은 0.00~0.02초 수준으로 정밀한 개선율을 계산하지 않는다. 전체 프로그램 로딩이나 수치 분석의 개선율은 아니다.

증거: `output/category-label-lookup-20260915`의 baseline.R, candidate.R, compare.R, run-1/2/3.log, times-1/2/3.csv, product-validation.log, data-io-validation.log. 연구 후보에 있던 불필요한 중괄호 블록은 제품 적용 시 제거했으며 제품 함수로 회귀 검사를 다시 수행했다.
