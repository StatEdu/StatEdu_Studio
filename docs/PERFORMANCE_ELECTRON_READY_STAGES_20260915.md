# Electron 초기 화면 준비와 관측 지연 분리

## 결과

최신 소스의 기존 측정에서 문서 로드 후 자동화 확인까지 약 0.92초가 걸렸다. 페이지 내부 표본을 추가한 3회 실행에서는 파일 버튼의 첫 표시·소켓 연결·busy 해제 조건이 문서 로드 후 0.511~0.547초에 처음 충족됐다. 기존 자동화 확인은 이보다 0.400~0.422초 늦었다. **0.92초 전체를 실제 UI 처리 시간으로 취급하면 안 된다.**

|조건(초)|실행 1|실행 2|실행 3|
|---|---:|---:|---:|
|문서 로드 → 버튼 첫 표시 및 첫 조건 충족|0.534|0.511|0.547|
|첫 조건 충족 → 기존 자동화 확인|0.422|0.420|0.400|
|실행 요청 → 첫 조건 충족|2.517|2.407|2.411|
|실행 요청 → 기존 자동화 확인|2.939|2.827|2.811|

페이지 내부에서 input과 버튼을 처음 관측한 뒤, 기존 `input.waitFor(attached)` 호출이 반환되기까지도 약 0.36~0.38초 차이가 있었다. trial 클릭 완료 구간은 약 0.03~0.04초였다. 이는 기존 순차 대기 방식이 최초 존재 시점을 정밀하게 기록하지 않는다는 증거다. 후속 반응형 처리도 있으므로 마지막 0.4초 전부를 불필요한 제품 지연이나 순수한 도구 비용으로 단정하지 않는다.

버튼 표시 이후에도 busy 상태가 바뀌었다. 전체 관측 중 busy=true 상태 진입은 9 / 9 / 7번이었다. 따라서 최초 조건 충족은 모든 초기 반응형 처리가 안정적으로 끝났다는 뜻이 아니다. 이 수치를 새 사용자 준비 시간으로 대체하거나 제품 코드에 조기 준비 신호를 추가하지 않았다.

## 방법과 한계

Electron 43.4.0과 현재 소스, 기존 번들 R 4.5.3을 사용했다. 이전 최신 소스 실험의 모듈 캐시를 재사용하고 별도 사용자 프로필을 사용했다. 제품 main/preload/package를 연구 launcher에 복사하고 **연구 main에만** dom-ready 시점의 페이지 계측 주입을 추가했다.

페이지 내부 `performance.now()`와 navigation loadEventEnd를 기준으로 비교했다. MutationObserver와 20ms 간격 표본으로 파일 input 존재, 버튼의 사각형 크기/visibility, Shiny 소켓 상태, shiny-busy 상태를 기록했다. 버튼 가림, 클릭 안정성, 모든 초기 출력의 완성까지 검사한 것은 아니다. 설치 시점은 loadEventEnd 후 약 36~47ms였으며 세 실행 모두 당시 버튼/input이 없었다. 첫 버튼 등장 이전에 계측이 시작됐음을 확인했다.

계측은 DOM/스타일을 읽는 추가 작업이므로 완전히 무부하인 프로파일이 아니다. 제품 결과 내용·수치·RNG의 새로운 검증은 아니다. 세 실행의 연결 이후 페이지 오류 및 확인 시점 표시 오류는 없었고 각 측정 프로세스의 종료를 확인했다. 연구 junction도 정상 종료 후 제거했다. 주요 제품 소스 해시는 이전 최신 소스 측정과 동일했다.

증거: `output/electron-ready-stages-20260915`의 `probe.js`, `observe.cjs`, `run.ps1`, 연구용 `launcher/main.js`, `result-1/2/3.json`, `summary.json`, `summarize.cjs`, `run.log`와 시작 로그. 제품 파일·설치 패키지는 변경하지 않았다.

다음 검토는 문서 로드 후 버튼 첫 표시까지 약 0.53초에 집중한다. 이미 효과가 없었던 언어 동기화 제거를 반복 적용하기보다 실제 초기 출력 생성·수신·DOM 반영 시각을 구분해야 한다.
