# 생존확률 시점 묶음 계산 검토 — 미적용 — 2026-09-14

## 결정

32개 시점을 묶어 지수함수를 계산하는 후보를 구현했다. 검증한 결과는 정확히 같았지만 전체 보정곡선 실행 시간이 증가하고 중간 벡터·행렬 할당량도 늘어 제품에 적용하지 않았다. 기존 시점별 계산을 유지한다.

## 후보

중복 위험도 재사용 경로에서, 유한한 누적위험이 두 개 이상이고 고유 위험도 수가 31,250 이하일 때만 후보를 사용했다. 나머지는 기존 계산으로 처리한다. 각 묶음에서 다음 순서를 유지했다.

1. 각 시점의 `-hazard * distinct_risk`를 기존 순서로 계산해 최대 32열의 행렬로 모은다.
2. 행렬에 `exp`를 한 번 적용한다.
3. 열마다 원래 관측치 순서로 복원한다.
4. 기존 `mean(values, na.rm=anyNA(values))`를 호출한다.

곱셈·지수의 개별 값 계산, 평균 입력의 순서·개수, 모형 재적합, 난수 추출, 부트스트랩 횟수 및 신뢰구간 계산을 유지했다. 행렬당 최대 원소 수를 100만 개로 제한했지만, 한 행렬의 제한이 전체 메모리 사용량 제한은 아니다.

## 전체 보정곡선 시간

번들 R 4.5.3, 시드 421, 600/2,000건, 3집단, 연속 공변량 1개, 사건 생성 확률 0.45, 부트스트랩 60회, 선택 시점 0·10·20의 합성 자료를 사용했다. 버전별 새 프로세스 세 개를 순차 실행했고 두 번째 비교는 후보를 먼저 실행했다. 조건별 준비 실행 후 프로파일러 없이 전체 `survival_adjusted_curve()`를 측정했다. 입력 생성·최초 모형 적합·로딩·화면·저장은 제외했다. 다른 R 작업은 시간 측정과 동시에 실행하지 않았다.

| 자료 | 기존 3회(초) | 후보 3회(초) | 중앙값 기존→후보 |
| --- | --- | --- | --- |
| 600건 | 0.93 / 0.92 / 0.93 | 1.05 / 1.01 / 1.00 | 0.93→1.01, 약 9% 증가 |
| 2,000건 | 5.56 / 4.46 / 4.47 | 5.80 / 5.96 / 6.57 | 4.47→5.96, 약 33% 증가 |

특히 2,000건에서 시간 변동이 있었지만 대응하는 세 비교 모두 후보가 느렸다. 다른 묶음 크기의 성능까지 단정하지 않으며, 이 결과를 기본 부트스트랩 2,000회나 전체 프로그램 시간으로 일반화하지 않는다.

## 할당 비용

실제 분석 시간 측정이 끝난 뒤 별도의 고정 벡터 실험을 수행했다. 고유 위험도 1,260개, 복원 후 관측치 2,000개, 누적위험 500개에 대해 준비 실행 후 Rprofmem으로 기록했다.

| 방식 | 누적 할당 바이트 | 가장 큰 단일 할당 바이트 |
| --- | ---: | ---: |
| 기존 시점별 계산 | 13,092,048 | 16,048 |
| 32시점 묶음 | 35,993,936 | 322,608 |

누적 할당량은 약 2.75배였다. 이는 해당 벡터 실험에서의 할당 기록이며 실제 전체 분석의 최대 메모리 또는 프로세스 RSS가 아니다. 지수함수 호출 수를 줄여도 행렬 구성과 열 추출에 추가 비용이 발생했다.

## 동일성 검증

- 72개 벡터 사례: 위험도 길이 1/2/50/2,000, 시점 수 1/2/31/32/33/65, 일반값·양/음의 0·극소/극대 유한값 조합. 기존 및 묶음 평균 벡터와 난수 상태가 정확히 일치했다.
- 실제 분석 600/2,000건 × 세 비교의 여섯 쌍에서 전체 결과, 경고/메시지, 표준 출력, 난수 상태가 `identical(..., num.eq=FALSE)`로 일치했다. 준비 실행과 측정 실행도 일치했다.
- 각 실제 분석에서 부트스트랩 60회 성공과 신뢰구간 제공을 확인했다.
