# Electron 첫 데이터 화면 출력 구간

## 결과

현재 소스의 Electron 계측을 3회 반복했다. 문서 로드에서 버튼 첫 표시까지 약 0.53초 중 가장 긴 구간은 소켓 연결 이벤트부터 첫 `data_steps` 출력 이벤트까지 약 0.44초였다. 제품 변경 없이 병목 후보를 좁혔다.

|구간(ms)|실행 1|실행 2|실행 3|
|---|---:|---:|---:|
|문서 로드 → Shiny 연결 이벤트|56.7|37.0|61.4|
|연결 이벤트 → 첫 data_steps 출력 이벤트|451.2|442.1|442.7|
|출력 이벤트 → 파일 버튼 첫 표시|33.1|38.8|26.3|
|문서 로드 → 파일 버튼 첫 표시|541.0|517.9|530.4|

동일 시작 로그의 최초 `render data_steps` 실행 시간은 0.038 / 0.039 / 0.037초였다. 약 0.44초 전체를 이 UI 생성 함수의 비용으로 설명할 수 없다. 연결 후 서버 초기화·다른 반응형 계산·출력 전달 및 클라이언트의 앞선 출력 처리가 함께 포함될 수 있다. 이번 계측만으로 이들 사이의 세부 비중을 확정하지 않는다.

## 계측과 범위

직전 `electron-ready-stages` 연구 구성을 복사하고 페이지 내부에서 `shiny:connected`, `shiny:value` 이벤트의 시각과 출력 이름만 추가 기록했다. 값이나 입력을 수정하지 않았다. 설치된 Shiny의 `receiveOutput()` 소스를 확인했으며 `shiny:value`는 출력 바인딩의 onValueChange 실행 전에 발생한다. **이는 서버가 패킷을 보낸 시각이나 WebSocket 원시 프레임 수신 시각이 아니다.**

MutationObserver 및 20ms 표본으로 기록한 버튼 표시 시각과 같은 페이지 performance 시계를 사용했다. 세 실행 모두 계측 설치 후 연결 이벤트가 관측됐고 최초 설치 시 input/버튼이 없었다. 클릭 가능 여부·모든 초기 처리가 안정화된 시각과 버튼의 첫 표시는 여전히 구분한다.

관측 종료까지 `data_steps` 출력 이벤트는 각 3번이었다. 원시 패킷 수나 서버 실행 횟수와 동일하다고 가정하지 않는다. R 로그에는 관측 종료 이후까지 포함한 추가 실행도 있다. 중복 제거가 유효한 최적화임을 입증하지 않으며, 이전에 전체 준비 시간을 줄이지 못했던 언어 동기화 후보를 재적용하지 않았다.

Electron 43.4.0, 현재 소스, 번들 R 4.5.3, 이전 최신 소스 실험의 모듈 캐시와 별도 프로필을 사용했다. 세 실행 모두 연결 이후 수집한 페이지 오류와 확인 시점 표시 오류가 없었다. 측정용 프로세스 종료 및 junction 제거, 주요 제품 소스의 해시 보존을 확인했다. 제품 분석 수치·RNG·내보내기의 신규 검증은 아니다.

증거: `output/electron-output-stages-20260915`의 `probe.js`, `observe.cjs`, `run.ps1`, `result-1/2/3.json`, `summarize.cjs`, `summary.json`, `run.log` 및 `startup-through-*.log`.

다음 단계는 연결 이후 첫 출력까지의 초기 서버 처리·출력 순서를 계측하는 것이다. 약 0.03초인 버튼 반영 경로를 먼저 재작성할 근거는 없다.
