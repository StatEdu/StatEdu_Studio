# 생존분석 최초 등록 JIT 후보 검토 — 2026-09-14

## 결론

생존분석 처리기를 등록하는 동안에만 JIT를 끄는 후보는 적용하지 않았다. 설정 단계의 작은 차이가 전체 흐름의 개선으로 이어지지 않았다. 실험 변경만 원복했으며 `R/server_survival.R`이 실험 직전 파일과 SHA256 기준으로 동일함을 확인했다. 이전에 적용한 `R/app_server.R`의 초기화 JIT 개선은 유지한다.

## 후보와 측정

생존분석 메뉴에 처음 진입하면 `register_survival_handlers`에서 KM·Cox·경쟁위험 분석의 처리기를 등록한다. 후보는 이 함수 본문에서 기존 JIT 수준을 저장하고 0으로 설정한 뒤 `on.exit`로 복원하는 두 문장이었다. 분석 수식이나 처리기 내용은 바꾸지 않았다.

번들 R 4.5.3, JIT 3, 기존 모듈 캐시, selected 가시성 모델로 새 프로세스에서 3쌍을 순차 측정했다. 두 번째 쌍은 순서를 반대로 했다. 변경 전 함수를 별도 환경에서 읽고 전역 환경으로 다시 연결해 비교했다. 프로파일을 사용하지 않은 실행의 중앙값은 다음과 같다(초).

| 단계 | 변경 전 | 후보 |
|---|---:|---:|
| 서버 초기화 | 0.75 | 0.75 |
| 상관분석 설정 | 0.50 | 0.50 |
| 첫 상관분석 | 0.46 | 0.46 |
| 생존분석 설정 | 1.16 | 1.14 |
| 첫 KM 분석 | 2.09 | 2.10 |
| 전체 흐름 | 5.57 | 5.57 |

전체 흐름 원자료는 변경 전 5.55/5.62/5.57초, 후보 5.57/5.60/5.55초였다. 전체 흐름에는 업로드, 설정, 첫 분석과 동일 입력 재실행이 포함된다. 재실행에는 기존 분석 캐시의 효과가 포함된다. 실제 Electron 로딩 시간이나 다른 데이터의 분석 성능으로 일반화하지 않는다.

## 검증과 해석

세 쌍 모두 분석 객체, 결과 HTML/의존성, 경고 및 알림이 `identical(...,num.eq=FALSE)`로 일치했다. 각 프로세스의 첫 실행과 동일 입력 재실행 결과도 일치했다. 분석 객체 및 HTML은 이전 전체 서버 검증본과도 일치했으며 경고는 0건이었다.

탐색용 설정 단계 Rprof에는 빈 이름과 여러 줄 표현식이 집계된 항목이 포함돼 있었다. 해당 집계 비율을 병목의 정량적 근거로 사용하지 않았다. 후보의 판단은 별도 비프로파일 실행의 단계별 경과 시간에 근거했다.

등록 구간의 JIT 제어를 추가 확대할 근거는 얻지 못했다. 다음 검토에서는 첫 KM 실행에서 그래프 생성·렌더링과 수치 계산 비용을 분리하는 것이 적절하다.

## 재현 자료

`output/analysis-setup-review-20260914/`에 `baseline.R`, `candidate.R`, `measure.R`, `compare.R`, `summary.csv`, 실행별 CSV/RDS가 있다. 원복 후에도 재현되도록 measure.R의 current 모드는 보관한 candidate.R을 명시적으로 읽는다. baseline/current 모두 함수 환경은 전역 환경으로 연결한다.

최종 측정은 `STATEDU_TEST_VISIBILITY=selected`, `STATEDU_TEST_INIT_JIT=on`으로 `measure.R baseline trial1` 또는 `measure.R current trial1` 형태로 실행했다. 번들 라이브러리, 자동 설치 비활성화, 기존 캐시 경로를 사용했다. `profile.R`와 `setup.Rprof`는 별도 탐색 자료다.

출력 변경이 없고 후보를 적용하지 않았으므로 PDF/Word/HWPX/Excel을 재검증하지 않았다. 설치 파일도 재빌드하지 않았다.
