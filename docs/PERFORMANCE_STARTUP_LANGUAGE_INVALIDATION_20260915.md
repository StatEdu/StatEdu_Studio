# 초기 데이터 화면 재출력 원인 추적

제품 코드 변경 없이 Shiny reactlog를 켠 실제 로컬 브라우저 세션에서 초기 데이터 화면 재실행 원인을 확인했다. 화면 관측과 서버 의존성 기록을 함께 사용했다. 이번 실행은 계측 비용이 포함된 원인 추적이며 새 성능 비교가 아니다.

## 확인한 연결

1. `www/easyflow.js`의 `easyflowScheduleAppLanguageSend()`는 0/100/500/1000ms에 `easyflowSendAppLanguage()`를 예약한다.
2. 자동 전송 함수는 `statedu_url_language`에 현재 언어를 `{priority: 'event'}`로 전송한다.
3. `R/app_server.R`의 `app_language` reactive는 세션에서 사용자가 선택한 언어가 아직 없으면 이 입력 등을 읽는다.
4. `R/server_data_outputs.R`의 `output$data_steps`는 `app_language_fn()`에 의존한다.

추적한 빈 초기 한국어 세션에서는 `statedu_url_language`의 값이 `ko`인 이벤트가 반복되면서 언어 reactive와 data_steps가 연달아 무효화됐다. 다른 입력이 변했다는 시간상 추측만이 아니라 reactlog의 의존성/무효화 기록에서 이 연결을 확인했다.

## 서버 기록

총 2,623개 reactlog 이벤트. 이번 세션 ID 체계에서 언어 reactive는 r43, 데이터 출력은 r241이었다. 이 ID는 다른 실행에서 달라질 수 있다.

|이벤트 인덱스|관측|
|---|---|
|1928→1930→1935|언어 입력 ko 변경 이벤트→언어 reactive 무효화→data_steps 무효화|
|2064→2066→2071|같은 ko 이벤트→같은 연결로 재무효화|
|2364→2366→2371|같은 ko 이벤트→같은 연결로 재무효화|

첫 전송은 초기 동기화 역할이 있을 수 있다. 뒤의 동일 값 전송까지 전부 없애도 안전하다고 결론 낸 것은 아니다. 앞선 브라우저 payload 비교에서 동일 data_steps 출력이 반복 전달된 관측과 이번 원인 추적이 연결된다.

파일 입력, header, DAT 구분자, 표 상태 등도 초기화 중 기록됐지만 위 세 data_steps 재실행의 무효화 시작은 언어 입력에서 확인됐다. 사용자 파일 로드·세션 복원·URL 언어 지정·언어 전환·소켓 재연결에 대해서는 이번 빈 초기 화면 관측만으로 일반화하지 않는다.

## 후속 후보

자동 초기 언어 동기화에서 같은 값을 반복 강제 이벤트로 보내는 부분만 중복 억제하는 후보를 시험한다. 사용자 언어 적용 이벤트, 적용 실패 시 폴백, 재연결 시 동기화는 유지해야 한다. 재시도 일정을 단순 삭제하거나 서버 언어 reactive를 고정하면 초기 연결/복원 경로를 깨뜨릴 수 있으므로 하지 않는다.

후보를 반영하기 전에 한국어/영어 초기 표시, URL 우선순위, 실제 언어 전환, 새 세션/재연결, 저장 설정 복원과 데이터 화면 갱신을 검증한다. payload 내용·초기 출력 횟수와 전체 준비 시간을 비교해 실제 이득을 확인한다. 이번에는 제품 코드에 후보를 적용하지 않았다.

## 재현 자료

`output/startup-data-invalidation-20260915/`의 launch.R, measure.cjs, inspect.R, reactlog.rds, result-1.json, 화면 PNG 및 서버 로그. launch.R은 계측 프로세스에만 `options(shiny.reactlog=TRUE)`를 설정하고 5초 뒤 기록을 저장했다. 브라우저는 화면 검사 후 기록 저장을 기다린 뒤 종료했다. 실제 제품 설정에는 reactlog를 켜지 않았다.

inspect.R의 r43/r241 필터는 보관한 단일 로그를 읽기 위한 것이며 새 실행에 자동 적용되는 범용 분석기가 아니다. 측정용 R과 Chrome은 종료했다. 통계/출력 내용/설치 파일 변경은 없다.
