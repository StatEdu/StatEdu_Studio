# 빈도분석 다중 이미지 캐시 — 2026-09-14

빈도분석 저장에 그림 종류·변수명을 구분하는 세션 캐시를 적용했다. 20개 그림의 반복 저장용 HTML 생성 중앙값은 2.11초에서 0.08초로 약 96.2% 줄었다. 첫 저장은 2.03→2.08초로 0.05초 늘었고, 별도 측정의 최대 메모리 중앙값은 291.5→311.4 MB로 약 19.9 MB 늘었다. 반복 저장 속도와 메모리의 교환 관계가 있는 변경이다.

## 구현과 제한

- `frequency_plot_data_uri`는 기존 렌더링 동작을 유지하는 기본 경로다. `saved_frequency_plot_blocks`, 저장용 HTML 함수와 직접 HTML/PDF/Excel 함수에 선택적 렌더러를 전달한다.
- `frequency_export_image_cache`는 기존 공통 캐시를 재사용하면서 안정된 래퍼 함수와 명시적인 결과·그림 종류·변수명·실제 그리기 함수를 키로 사용한다. 매 호출마다 만들어지는 익명 함수 환경 때문에 발생하던 재사용 실패를 피한다. 그리기 함수가 바뀌어도 키가 달라진다.
- 공통 캐시에 `max_entries` 선택 인자만 추가했다. 기존 상관·PCA·EFA의 기본값 2개는 유지한다. 빈도분석은 최대 64개·`object.size` 추정 합계 16 MiB로 제한한다. 실제로 보관 가능한 그림 수는 각 항목 크기에 따라 64개보다 적을 수 있다.
- 결과와 문맥(DPI, R 옵션, 로케일, 작업 폴더, Windows 그래픽 설정·폰트), 그림 크기·해상도를 정확히 비교한다. 경고·메시지 또는 RNG 변경이 있는 그림은 보관하지 않는다. 임의의 표준 출력까지 감지하는 범용 캐시는 아니며 실제 그리기 출력의 동일성은 별도로 검증했다.
- 새 분석 결과 설정, 선택 초기화, 세션 종료 시 캐시를 비운다. 표와 문서 구성은 매번 기존 경로로 만든다. 직접 그림 파일 저장, 통계 계산, 표시 내용, 해상도·장치, 누적 스냅샷 변환은 유지한다.
- 바이트 한도는 전체 프로세스 메모리나 환경 참조 전체의 상한이 아니다. 한도를 넘는 항목은 보관하지 않거나 이전 항목을 제거한다. 그림이 많아 캐시에 모두 들어가지 않으면 반복 저장의 이득이 줄거나 없어질 수 있다. 출력은 기존 렌더링으로 완성한다.

## 성능

번들 R 4.5.3, Windows, seed 714, 2,000행 자료, 기본 600 dpi다. 범주변수마다 원·막대 그림, 연속변수마다 히스토그램·상자·바이올린 그림을 켰다. 5개 사례는 범주 1개·연속 1개, 20개는 범주 4개·연속 4개다.

각 사례·방식별 새 프로세스 3개, 총 12개를 순차 실행했다. 2회차는 방식 실행 순서를 바꿨다. 분석과 모듈 로딩 후 HTML 생성만 측정했으며 다른 R 검증·파일 변환·메모리 관측은 동시에 하지 않았다.

| 그림 수 | 방식 | 첫 저장 3회(초) | 반복 저장 3회(초) | 첫 / 반복 중앙값 |
|---|---|---|---|---|
| 5 | 기존 | 0.79 / 0.75 / 0.76 | 0.50 / 0.47 / 0.47 | 0.76 / 0.47초 |
| 5 | 캐시 | 0.75 / 0.77 / 0.75 | 0.05 / 0.03 / 0.03 | 0.75 / 0.03초 |

20개 반복 저장 HTML 생성의 감소율은 약 96.2%, 5개는 약 93.6%다. 대화상자와 PDF 등 파일 변환은 포함하지 않으므로 전체 파일 저장에 같은 감소율을 적용할 수 없다.

## 메모리와 수명

20개 그림 사례의 별도 새 프로세스 3쌍에서 실제 R PID의 Windows `PeakWorkingSet64`를 관측했다. 패키지 로딩·분석·첫/반복 HTML 생성·검증 자료 저장을 포함한 프로세스 전체 최고치다. MB는 1,000,000 bytes다.

| 회차 | 기존 최대 MB | 캐시 최대 MB |
|---|---:|---:|
| 1 | 282.100 | 311.374 |
| 2 | 291.627 | 311.452 |
| 3 | 291.516 | 311.407 |
| 중앙값 | 291.516 | 311.407 |

중앙값은 19.890 MB(약 6.8%) 증가했다. 캐시 항목의 `object.size` 추정 합계는 5개 사례 2,975,600 bytes, 20개 사례 14,051,208 bytes였다. 이 추정치는 프로세스 메모리 증가량과 같지 않으며 공유 객체·함수 표현의 중복 계산 등이 포함될 수 있다. 실제 서버에서 새 분석·초기화·종료 후 항목이 0개임을 확인했으며, OS에 즉시 메모리가 반환된다는 의미는 아니다.

## 정확성·서버·상한 검증

- 속도 측정 6쌍과 메모리 측정 3쌍에서 HTML 전체(내장 PNG), 경고·메시지·표준 출력·RNG가 `identical(..., num.eq=FALSE)`로 일치했다. 각 실행의 첫·반복 출력도 같고 분석 결과 직렬화 값이 변하지 않았다.
- 변경 전 소스와 캐시 경로를 12조건에서 비교했다: 기본, 반복, 보고서 모드, CSS, 소수점 쉼표 표시, 영어, 변수 라벨, 300 dpi, 결측 자료, 범주변수만, 연속변수만, 그림 없음. 모두 동일했다.
- `scripts/validate_frequency_export_image_cache.R`: 20개 그림 반복 적중, 결과·종류·변수명·실제 그리기 함수·문맥·크기·해상도 변경, 독립 객체, 초기화, 항목·바이트 한도를 검증했다. 기존 공통 캐시 테스트도 재실행해 기본 2개 제한과 경고·메시지·RNG·오류 우회를 확인했다.
- 1 byte 한도의 실제 PNG 검사에서도 첫·반복 HTML과 5개 그림이 변경 전과 같았다. 캐시는 비어 있고 렌더링은 총 10회 수행되어 한도 초과 시 정상 경로로 완성됨을 확인했다.
- 실제 앱 서버를 MockShinySession에서 실행했다. 분석 후 HTML 두 번·PDF·Excel 저장에 PNG 생성은 총 5회였다. 재분석 후 다음 저장에서 다시 5개를 만들고 초기화·종료 시 비웠다. 이 서버 검사에서 PDF 변환은 입력 HTML 기록용 대체 함수였으며 별도 직접 저장 검사에서는 실제 변환기를 사용했다.
- 실제 직접 HTML·PDF·Excel 함수도 동일 캐시에서 총 5회의 PNG 생성으로 저장을 완료했다.
