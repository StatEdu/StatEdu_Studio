# Cox 진단 공변량의 고유값 조건 조기 확인 — 2026-09-14

> 검증 범위 정정 (2026-09-14): 아래의 경쟁위험/Fine–Gray 전체 결과 검증 표현은 당시 `integration.R`이 `regression`을 지정하지 않아 기본 CIF/Gray 경로만 실행한 것을 잘못 기술한 것이다. 그 검증은 원인별 Cox 또는 Fine–Gray 회귀 검증으로 볼 수 없다. 직접 함수 및 Cox 검증 결과는 별개다. 이후 `regression="both"`를 명시한 600행·20공변량 자료에서 초기 Cox 최적화 전과 현재 모듈 전체의 결과·진단·난수 상태를 비교해 통과했다. 상세 내용은 [원인별 Cox 저장·통합 검증](COMPETING_PH_EXPORT_VALIDATION_20260914.md)을 참고한다.

`survival_cox_functional_form_data`의 연속형 공변량 선택 조건은 유한한 서로 다른 값이 4개 이상인지 확인하는 것이다. 속성 없는 숫자 벡터에서 앞의 네 값이 모두 유한하고 서로 다르면 조건 충족이 확정되므로, 전체 유한값 벡터와 고유값 목록을 만들지 않고 TRUE를 반환하도록 적용했다.

이는 일부 자료로 전체 분포를 추정하는 근사 방법이 아니다. 네 값만으로 조건을 입증할 수 있는 경우에만 조기 반환한다. 앞부분에 중복·결측·무한값이 있거나 길이가 짧거나 속성/클래스가 있으면 기존 전체 검사로 돌아간다. 선택 이후 행 필터링, 진단 값, 자료형과 결과표 구성은 유지한다.

## 측정

번들 R 4.5.3, 앱 설정 적용, 자동 설치 비활성화. 새 프로세스에서 변경 전후 3쌍을 순차 실행하고 두 번째 쌍은 역순으로 했다. 각 프로세스는 1천 행 다음 10만 행, 숫자 공변량 10개와 유한 잔차를 실행했다. 메모리 계측과 검증은 시간 측정과 분리했다.

| 입력 행 수 | 변경 전 3회(초) | 변경 후 3회(초) | 중앙값 전→후 |
|---|---|---|---|
| 1,000 | 0.01 / 0.01 / 0.02 | 0.02 / 0.01 / 0.02 | 0.01→0.02 |
| 100,000 | 0.03 / 0.03 / 0.03 | 0.02 / 0.00 / 0.02 | 0.03→0.02 |

짧은 실행의 측정 해상도와 변동을 고려해 큰 속도 향상률을 주장하지 않는다. 작은 조건에서는 중앙값이 0.01초 증가했다. 시간은 진단용 자료 생성 함수 전체이며 적합·다른 진단·UI·앱 로딩·내보내기는 포함하지 않는다. 앞부분 중복이 많은 대용량 자료의 성능은 별도로 측정하지 않았다.

Rprofmem은 각 함수를 3회 준비 실행하고 gc() 후 1회 호출했다. 10만 행·10공변량의 기록된 누적 할당량은 94,891,920→52,402,720바이트로 42,489,200바이트(약 42.49MB, 44.8%) 감소했다. 최대 메모리나 프로세스 RSS 감소를 뜻하지 않는다.
