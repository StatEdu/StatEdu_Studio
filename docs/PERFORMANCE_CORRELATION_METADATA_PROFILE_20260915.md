# 상관분석의 전체 변수 정보 크기에 따른 비용

2026-09-15. 제품 코드를 변경하지 않고 선택한 분석 변수는 고정한 채 전체 변수 정보의 크기만 달리하여 측정했다. 기존의 작은 상관분석 후보를 반복하는 대신 미선택 변수 정보가 많은 조건을 조사했다.

## 최종 측정 조건

`scripts/profile_correlation_metadata.R`에서 실제 서버 시작과 같이 `statedu_apply_preferences(statedu_initial_preferences())`를 먼저 수행한다. 시드 20260915, 정규 난수 1,000행·20개 연속 변수, Pearson 지정, 정규성 표 활성화 조건이다. 전체 변수 정보는 20행 또는 10,000행이며, 앞 20개 이름·라벨·측정수준은 동일하다. 추가 변수 정보는 분석 대상 데이터에 포함되지 않는 이름이다.

독립 R 프로세스 두 개에서 조건 순서를 뒤집었다. 조건별 사전 호출 후 3회 측정 중앙값을 기록했다. `Sys.time()` 측정에는 전체 결과 준비와 진단/stdout 캡처가 포함되고, 데이터 생성과 명시적 GC는 제외된다. 프로파일은 별도 3회 호출에서 10ms 간격으로 수집했다.

| 전체 변수 정보 | 실행 1 중앙값 초 | 실행 2 중앙값 초 |
|---|---:|---:|
| 20개 | 0.038499 | 0.039118 |
| 10,000개 | 0.194682 | 0.198261 |

선택된 분석 변수와 쌍 수는 같지만 큰 변수 정보 조건에서 약 0.16초가 추가됐다. `correlation_measurement()`가 호출될 때마다 `correlation_measurement_lookup()`에서 전체 측정수준 열을 `tolower(as.character(...))`로 변환한다. 전체 분석의 사전 검사와 정규성 준비에서 이 조회가 반복된다.

큰 변수 정보 조건의 프로파일에서 `tolower` 자체는 표본 시간의 73.91% / 80.85%를 차지했다. 표본 시간 합계는 0.46초 / 0.47초로 작으므로 세부 백분율은 대략적인 경로 확인에만 사용한다. 변수 정보의 크기에 따른 전체 시간 차이와 코드의 반복 조회를 함께 확인한 결과다.

## 결과 확인

190쌍 결과가 생성됐음을 확인했다. 사전 호출, 모든 시간 측정 및 프로파일 호출에서 결과 객체 전체, 진단, stdout, RNG를 `identical(..., num.eq=FALSE)`로 비교했다. 작은/큰 변수 정보의 결과는 모두 일치했고, 환경 속성 제거 등 정규화는 사용하지 않았다. 아래 초기 하네스 결과와도 동일했다.

## 초기 하네스 정정

초기 스크립트는 서버의 환경설정 적용 단계를 빠뜨렸다. 그 상태에서는 숫자·p값 표시 설정 조회가 설정 파일 읽기로 되돌아가, 전체 결과 준비가 약 1.92~2.16초로 측정되고 파일 접근이 프로파일을 지배했다.

실제 `R/app_server.R`는 시작 시 환경설정을 적용하므로 이 값을 앱의 병목이나 성능 기준으로 사용하지 않는다. 초기 기록은 상위 출력 디렉터리에 보존하고 최종 기록을 `server-initialized/`에 분리했다. 초기→최종 차이는 제품 개선율이 아니라 측정 초기화 오류의 수정이다.

## 판단과 후속 작업

다음 후보는 정상적인 변수 정보에서 측정수준 조회표를 분석 호출 안에서 재사용하는 것이다. 중복 이름, 누락된 측정수준, 비정상 형식과 진단 순서의 계약을 검증한 뒤 적용 여부를 판단한다. 계산식·결측 처리·추정법·표시 자릿수는 바꾸지 않는다.

이번에는 코드 변경이나 개선율을 주장하지 않는다. 실제 UI, 전체 로딩 또는 내보내기 성능 측정도 아니다.
