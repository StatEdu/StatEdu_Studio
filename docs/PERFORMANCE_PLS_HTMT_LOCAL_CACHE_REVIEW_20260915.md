# PLS 재표집 내부 HTMT 상관 재사용 검토 — 미반영

## 후보

현재 PLS 부트스트랩은 매 반복에서 `seminr:::HTMT(boot_model)`을 계산한다. 이 함수는 구성개념 쌍마다 각 구성개념 내부 상관행렬을 다시 계산한다. **한 번의 HTMT 호출 안에서만** 동일한 일반 숫자 행렬의 자기 상관 결과를 재사용하는 후보를 만들었다. 서로 다른 재표집 사이에는 공유하지 않는다.

로컬 함수 사본의 `stats::cor` 참조를 캐시 함수로 바꿨다. x와 y가 속성까지 정확히 같은 일반 숫자 행렬일 때만 캐시를 조회하며, 경고·메시지를 발생시킨 계산은 저장하지 않았다. HTMT의 절댓값·합계·분모 산식과 계산 순서는 유지했다. 매 HTMT 호출마다 캐시와 함수 환경을 새로 만든다. 이 준비 및 행렬 비교 비용도 전체 시간에 포함된다.

이는 9월 13일 적용한 `structural_canvas_htmt()`의 내부 평균 재사용과 다른 경로다. 당시 후보를 되돌리거나 수정하지 않았다. 이번 후보는 `output`의 연구 스크립트 안에만 있으며 제품 및 seminr namespace는 변경하지 않았다.

## 측정 결과

번들 Windows R 4.5.3, 기존 PLS 재현성 fixture의 120행·9지표·3개 구성개념, 완전자료 composite PLS, 부트스트랩 500회, seed 24680, 작업자 1개. 새 프로세스 3개를 순차 실행했고 두 번째는 후보부터 측정했다. 기준·후보 부트스트랩 함수를 모두 `cmpfun`으로 컴파일하고 각각 한 번 실행한 뒤 전체 반환 캡처를 측정했다. 정확한 동일성 검사는 타이머 밖에서 수행했다.

|실행|기준(초)|후보(초)|
|---|---:|---:|
|1|2.21|2.20|
|2|2.21|2.22|
|3|2.15|2.22|
|중앙값|2.21|2.22|

1회 소폭 감소, 2회 증가였으며 중앙값도 개선되지 않았다. **후보를 적용하지 않는다.** 캐시 준비 및 행렬 비교 비용을 포함한 이 구현에서 이득을 얻지 못했다는 결론이며, 모든 크기의 모형에서 HTMT 재사용이 느리다는 결론은 아니다. 작은 단일 모형·직렬 조건이므로 5,000회·병렬·PLSc·고차 구성개념·잠재 조절로 일반화하지 않는다. 다음에는 실제 앱 작업 경로와 원래 반복 수의 기준 측정을 우선하고 이 후보를 근거 없이 반복 시험하지 않는다.

## 정확성

- HTMT 직접 입력 8종: 일반, 결측, 상수, Inf, 매우 가까운 값, 큰 값, 동일 지표, 열 순서 변경. 각 프로세스에서 원본과 후보의 전체 값·속성·경고·메시지·오류·표준 출력·RNG를 `identical(..., num.eq=FALSE)`로 비교해 모두 통과했다. 비정상 입력은 오류 캡처까지 비교하며 모두 유효 통계량을 반환했다는 뜻은 아니다.
- 세 프로세스에서 사전 및 측정 실행의 전체 500회 부트스트랩 캡처가 각 프로세스 기준과 정확히 같았다. 기준은 요청/유효 반복 500회를 확인했고, 비교에는 유효 위치, 반환 추정 배열과 최종 요약, 진단, RNG를 포함했다.
- 병렬 작업자에는 후보를 배포하지 않았고 병렬 결과나 작업자 진단 동일성을 주장하지 않는다.

재현: `output/pls-htmt-local-cache-20260915/check.R`, `times-1.csv`~`times-3.csv`. 연구 스크립트는 현재 제품과 설치된 seminr에서 함수를 읽으므로 버전/소스가 바뀌면 같은 후보라고 단정할 수 없다.

제품 PLS 엔진 SHA256은 전후 동일: `7FAF3D4541FDCA1ED325D1CF01F398EDDC718A7E9948973832DB084CF8587A49` (`R/setup_custom_model_canvas_structural_pls_engine.R`). 출력·내보내기 구현과 설치 파일은 변경하지 않았다.
