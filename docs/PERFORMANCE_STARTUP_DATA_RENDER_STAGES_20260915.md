# 초기 데이터 화면 출력 도착·표시·재전송 계측

이전 로컬 화면 측정에서 세션 연결 후 데이터 입력 화면이 늦게 채워지는 구간을 분리했다. 실행 코드는 변경하지 않았다. 부트스트랩이나 통계 계산 성능 측정은 아니다.

## 계측 방식

현재 `run_app.R`, 번들 R 4.5.3, headless Chrome, 초기 한국어 화면, 미로드 데이터, 유효 모듈 캐시 조건이다. 새 R 프로세스 및 새 브라우저 컨텍스트를 3회 순차 실행했다. Chrome 프로세스 자체 시작은 타이머 밖이고 Electron 시작 및 캐시 miss는 제외했다.

연구용 브라우저 init script가 WebSocket의 open/message를 관찰했다. 실제 메시지를 수정하거나 차단하지 않고 `data_steps` 포함 출력의 도착 시각과 출력 키만 기록했다. MutationObserver로 파일 입력 요소 삽입과 버튼의 표시를 관측했다. 버튼 표시 판정은 폭이 0보다 크고 visibility가 hidden이 아닌 조건이며, 클릭 가능 검사는 별도의 Playwright trial click에서 확인했다.

수치는 브라우저 내 `performance.now()`의 동일 기준점 간 차이다. Node의 프로세스 시작 타이머와 브라우저 시각을 직접 빼지 않았다. 각 페이지에서 관측한 첫 output_message가 data_steps를 포함함을 확인했다.

## 최종 3회 관측

|구간|1회|2회|3회|중앙값|
|---|---:|---:|---:|---:|
|소켓 open→첫 데이터 출력 메시지|421.8ms|397.1ms|406.4ms|406.4ms|
|첫 메시지→파일 선택 버튼 최초 표시|42.9ms|44.0ms|54.4ms|44.0ms|
|R 시작→기존 준비 완료 검사 통과|2.5057초|2.4004초|2.4050초|2.4050초|

첫 구간은 서버 세션 초기화·다른 출력 처리·직렬화·전송·이벤트 전달을 합친 관측 시간이다. 이를 data_steps 함수 하나의 계산 시간으로 해석하지 않는다. 두 번째 구간도 HTML/의존성 적용 및 브라우저 이벤트 처리 비용을 포함한다. 기록된 준비 완료 시간은 locator 대기·trial click·busy 해제·두 프레임 대기를 포함하므로 버튼 최초 표시 시각과 같지 않다.

서버 3회차 로그에서 전체 세션 초기화는 약 0.157초, 첫 data_steps 생성은 약 0.047초, 이후 같은 함수 실행은 약 0.003~0.005초였다. 이 로그만으로 약 0.4초 구간 전체의 원인을 설명하지 못한다. 겹치는 함수 및 대기 시간을 합산하지 않는다.

## 반복 출력 확인

최종 브라우저 캡처 시점까지 data_steps payload는 각 페이지에서 4/3/3번 관측됐다. 첫 payload 이후 각각 3/2/2개가 직전 payload와 `JSON.stringify()` 문자열 기준으로 정확히 같았다. 모두 3,197문자였다. 이는 HTML과 의존성 등을 포함해 브라우저가 받은 해당 payload의 동일성이지, 모든 Shiny 출력·R 객체·세션 상태의 동일성을 뜻하지 않는다. 관측 종료 후의 출력이나 다른 사용자 동작은 포함하지 않는다.

초기화 시 동일한 데이터 입력 화면이 반복 전송되는 후보를 확인했다. 하지만 제거했을 때 준비 시간이 단축되는지는 아직 시험하지 않았다. 이미 같은 출력이 나왔다고 해서 뒤이은 입력 복원이나 이벤트 바인딩을 무조건 생략해서는 안 된다. 현재 기록은 비어 있는 초기 화면 하나뿐이다.

다음 검토 대상은 `R/server_data_outputs.R`의 `register_data_workspace_outputs()`와 초기 입력 설정 경로다. `output$data_steps`가 구독하는 입력·상태 중 무엇이 초기 재실행을 유발하는지 추적하고, 파일 로드/세션 복원/언어 변경에서도 내용과 입력 바인딩을 유지하는 경우에만 후보를 시험한다. 동일 HTML 캐시만 추가하면 서버 계산은 줄어도 반복 전송과 DOM 적용은 남을 수 있으므로 전체 화면 준비 시간을 다시 측정해야 한다.

## 산출물과 한계

`output/live-startup-render-stages-20260915/measure.cjs`, result-1~3.json, ready-1~3.png, server-1~3.log, startup-1~3.log. JSON의 stages에 브라우저 이벤트 및 payload 동일성 판정이 기록돼 있다. 초기 단계 관측 뒤 payload 비교를 추가해 다시 측정했으며 JSON/PNG/서버 출력 로그는 최종 실행이다. startup 로그는 append 방식으로 두 실행 묶음이 함께 있어 마지막 블록을 사용해야 한다.

3회 모두 pageerror와 표시된 Shiny 오류가 없었다. 실제 파일 업로드나 통계 결과의 동등성을 검증한 것은 아니다. 개발 환경의 계측이므로 별도 Electron 설치본, 큰 데이터, 느린 기기 또는 초기 캐시 생성으로 일반화하지 않는다. WebSocket 관찰 코드의 추가 비용도 포함된다. 제품·패키지·설치 파일은 변경하지 않았다.
