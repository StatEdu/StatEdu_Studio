# StatEdu Studio 전체 분석 성능 감사 (2026-08-27)

## 목적과 원칙

- 분석 메뉴 로딩, 분석 계산, 결과표 생성, 부트스트랩을 분리해 측정했다.
- 비교 기준은 일요일 버전 `f74d299`(2026-08-23)과 현재 기준 커밋 `9fa2338` 및 본 감사의 미커밋 성능 수정이다.
- 통계량, p 값, 신뢰구간, 유효 부트스트랩 판정 등 분석 결과가 달라지는 최적화는 허용하지 않았다.

- 계산/표 시간은 고정 seed의 대표 자료를 사용했다. 계산, R UI 객체 생성, HTML 직렬화를 따로 측정했다.

## 결론

1. 최종 35개 분석 메뉴의 평균은 **0.712초**, 중앙값은 **0.632초**다. 30/35개가 1초 미만이고 최댓값은 1.764초다.
2. 일요일의 평균 3.533초, 중앙값 2.852초와 비교하면 각각 **79.8%, 77.8% 단축**됐다.
3. 결과표의 공통 지연 원인은 레이블 하나를 번역할 때마다 전체 분석 레이블 약 330개를 다시 생성하던 구조였다. 레이블 사전을 세션 내에서 캐시해 대표 결과표 작성 시간을 **88.3~93.6% 단축**했다.
4. CFA 진입 시 CFA·CB-SEM·PLS-SEM을 모두 등록하던 구조를 메뉴별 등록으로 분리했다. 공유 등록 4.834초가 CFA 0.747초, CB-SEM 0.724초, PLS-SEM 0.661초로 분리됐다. 분석 추천 화면은 더 이상 세 모듈을 미리 등록하지 않는다.
5. 계산 엔진은 변경하지 않았다. 전체 외부 기준 비교 66행, SEM 캔버스/결과 UI/화면-표 계약, 설치본 회귀 게이트가 모두 통과했다.

## 5. 부트스트랩 분석

일요일판과 같은 장비에서 연속 A/B로 측정한 기존 통제 비교가 버전 비교의 기준이다. 본 감사 중 단독 재측정 두 번은 시스템 전반이 약 1.8~2.0배 함께 변동했다. 회귀 0.36→0.65초, ICC 0.12→0.22초, 벌점회귀 33.17→64.75초, Cox 13.04→26.11초처럼 모든 경로가 같은 비율로 움직여 코드별 회귀가 아니라 전원/백그라운드 부하 변동으로 판단했다.

| 분석/경로 | 반복 | 통제된 현재 | 일요일 | 판단 |
|---|---:|---:|---:|---|
| 일반 회귀 계수 bootstrap | 5,000 | 0.22초 | 0.22초 | 동일 |
| 평가자간 ICC CI | 1,000 | 0.07~0.08초 | 0.06~0.08초 | 동일 |
| 벌점회귀 선택 bootstrap | 500 | 첫 20.38초 / 이후 8.05초 | 25.63~29.79초 | 첫 실행도 단축, 이후 2.53배 추가 단축 |
| Cox 보정 생존곡선 | 2,000 | 8.90~8.92초 | 8.92~8.96초 | 동일 |
| 매개·조절, X 2개 | 총 10,000 | 11.94초 | 12.55초 | 소폭 빠름 |
| 완전자료 일반 SEM | 5,000 | 31.19초 | 92.86초 | 약 3배 빠름 |
| 결측 10% 일반 SEM(FIML) | 5,000 | 144.66초 | 234.76초 | 38.4% 단축 |
| 잠재변수 product SEM | 5,000 | 149.22초 | 152.09초 | 동일 |
| CFA 신뢰도 bootstrap | 1,000 | 11.16초 | 15.49초 | 28.0% 단축 |
| PLS-SEM | 5,000 | 12.05초 | 9.46초 | 2.59초 증가, 절대시간은 짧음 |

결측 FIML과 잠재변수 product SEM은 여전히 전체 분석 중 가장 오래 걸린다. FIML은 결측 패턴별 likelihood·정보행렬을 반복 계산하므로 완전자료보다 느리다. 이미 표본 인덱스 전송, 최대 12개 작업자, 기대정보 유효성 검사를 적용했고 기존 `lavaanList`와 원계수·표준화계수·유효 마스크·최종 요약이 허용오차 0으로 검증됐다. 작업자 15개, 고정 시작값, 가중 중복행 압축은 각각 더 느리거나 결과를 바꿔 채택하지 않았다.

벌점회귀 선택 안정성은 LASSO와 Elastic Net에서 각각 500회 교차검증을 재적합한다. 첫 실행에서는 Windows 작업자와 `glmnet`의 차가운 시작 비용(측정 27.03초)이 병렬 이득보다 커서 직렬로 실행하되, 안정성 계산에 사용하지 않는 fold 예측행렬을 보관하지 않아 19.98초에서 18.20초로 줄였다. 앱 세션에서 첫 계산이 끝난 뒤에는 패키지 파일이 준비된 것으로 표시하고, 다음 계산부터 각 반복의 표본 seed와 교차검증 seed를 그대로 유지한 채 4개 작업자에 분배한다. 실제 자동 경로 재검증은 첫 20.38초, 다음 8.05초였고 두 반환 객체 전체가 `identical()`로 일치했다. 작업자 초기화나 병렬 실행이 실패하면 직렬 계산으로 자동 복귀한다.
