# 주성분분석 저장 이미지 캐시 — 2026-09-14

주성분분석(PCA)의 HTML·PDF·Excel 저장 처리에 세션별 이미지 캐시를 적용했다. 동일한 결과를 반복 저장할 때 저장용 HTML 생성 중앙값이 0.77초에서 0.17초로 약 77.9% 줄었다. 첫 저장은 0.88초에서 0.87초로 거의 같았다.

## 구현

- 기존 상관분석의 `correlation_export_image_cache()`를 재사용한다. 공통 캐시 구현을 복제하거나 변경하지 않았다. PCA는 별도 캐시 객체를 생성하므로 상관분석과 항목을 공유하지 않는다.
- `pca_results_ui`, `saved_pca_results_html`, 직접 HTML/PDF/Excel 저장 함수에 선택적 `plot_renderer` 인자를 전달한다. 기본값은 기존 `plot_data_uri`다.
- 실제 PCA 저장 이벤트는 같은 캐시를 전달한다. 스크리 그림과 바이플롯의 PNG만 재사용하며 표·문서 구성은 매번 기존 경로로 만든다. 앞서 적용한 JIT 복원 처리는 유지한다.
- 새 분석이 성공했을 때, 선택 초기화, 세션 종료 시 캐시를 비운다. 분석 실패는 기존 결과와 캐시를 유지한다.
- 캐시 키는 결과 전체, 그리기 함수, 폭·높이·해상도, DPI, R 옵션, 로케일, 작업 폴더, Windows 그래픽 설정과 폰트를 정확히 비교한다. 경고·메시지 또는 RNG 변경이 있는 그리기는 저장하지 않는다. 임의의 표준 출력까지 감지하는 범용 캐시는 아니며 실제 두 그리기 함수의 표준 출력 동일성은 별도로 검증했다.
- 보관 항목은 최대 2개, `object.size` 추정 합계는 최대 16 MiB다. 초과 항목은 보관하지 않는다. 이 제한은 전체 프로세스나 환경의 재귀적 참조 전체에 대한 메모리 제한이 아니다.

개별 그림 파일 저장은 기존 경로다. 누적 결과의 파일 변환은 이미 저장된 스냅샷을 사용한다. 통계 계산식, 표시 내용, PNG 해상도·장치는 변경하지 않았다.

## 성능

번들 R 4.5.3, Windows, seed 714, 2,000행·20변수, 상관행렬 PCA, 고정 2성분, 회전 없음, 두 그림 켜짐, 600 dpi. 각 방식 새 프로세스 3개를 순차 실행하고 두 번째 회차는 순서를 반대로 했다. 분석과 모듈 로딩을 완료한 뒤 측정했다. 메모리 관측 및 다른 R 검증은 타이밍 실행과 분리했다.

| 회차 | 기존 첫 저장 | 캐시 첫 저장 | 기존 반복 | 캐시 반복 |
|---|---:|---:|---:|---:|
| 1 | 0.89초 | 0.86초 | 0.94초 | 0.17초 |
| 2 | 0.88초 | 0.87초 | 0.75초 | 0.17초 |
| 3 | 0.86초 | 0.87초 | 0.77초 | 0.17초 |
| 중앙값 | **0.88초** | **0.87초** | **0.77초** | **0.17초** |

기존 방식에도 직전 JIT 개선이 적용되어 있다. 수치는 **저장용 HTML 생성**이며 파일 선택·PDF 등 변환 시간은 포함하지 않는다. 모든 자료에서 전체 저장이 78% 빨라진다는 의미가 아니다.

## 메모리와 수명

같은 자료의 별도 새 프로세스 3쌍에서 실제 계산 PID의 Windows `PeakWorkingSet64`를 관측했다. 패키지 로딩·분석·첫/반복 HTML 생성·검증 자료 저장까지 포함한 프로세스 전체 최고치다. MB는 1,000,000 bytes다.

| 회차 | 기존 최대 MB | 캐시 최대 MB |
|---|---:|---:|
| 1 | 396.521 | 393.167 |
| 2 | 392.196 | 392.286 |
| 3 | 392.479 | 391.565 |
| 중앙값 | 392.479 | 392.286 |

차이가 작아 메모리 절감으로 해석하지 않는다. 저장 후 캐시 항목은 2개, 추정 보관량은 3,448,384 bytes로 세 회차 모두 같았다. 실제 서버 테스트에서 새 분석·초기화·세션 종료 후 보관 항목이 0개임을 확인했다. OS에 메모리가 즉시 반환되거나 모든 장시간 세션에 누수가 없다는 검증은 아니다.

## 검증

- 속도 측정 3쌍과 메모리 측정 3쌍의 HTML 전체(내장 PNG 포함), 경고·메시지·표준 출력·RNG가 `identical(..., num.eq=FALSE)`로 일치했다. 각 실행의 첫·반복 생성도 동일하고 분석 결과 직렬화 값이 변하지 않았다.
- 변경 전 소스와 적용 후 캐시 경로를 12조건에서 비교했다: 기본, 보고서 모드, 사용자 CSS, 소수점 쉼표 표시, 영어, 변수 라벨, 300 dpi, 그림 끄기, 1성분, varimax, 공분산행렬, 결측 자료. 모든 HTML·PNG·조건·출력·RNG가 일치했다.
- 기존 공통 캐시 검증을 재실행해 키·인자·함수·문맥 변경, FIFO 제한, 세션별 객체 분리, 초기화, 크기 초과 및 경고·메시지·RNG·오류 시 우회를 확인했다. PCA JIT 0~3의 정상·오류 복원 검사도 통과했다.
- 실제 앱 서버를 MockShinySession에서 실행했다. PCA 메뉴 진입, 분석, HTML 두 번·PDF·Excel 저장까지 PNG 생성은 2회였다. 같은 자료로 다시 분석하면 캐시가 비워지고 다음 저장에서 다시 2개를 만들었다. 선택 초기화와 세션 종료도 비웠다. 이 서버 검사에서 PDF 변환은 입력 HTML 기록용 대체 함수였으며, 별도 직접 저장 검사에서는 실제 PDF 변환기를 사용했다.
- 별도 직접 HTML·PDF·Excel 저장 함수도 동일 캐시로 PNG를 정확히 2회 생성했다.

## 현재·누적 5종 출력

240행·8변수 PCA 스냅샷으로 HTML/PDF/Word/HWPX/Excel 현재·누적 총 10개 파일을 기존 변환기로 생성했다. 현재는 단일 스냅샷, 누적은 다른 ID로 같은 결과를 두 번 추가한 목록이다. 직접 저장 파일 3개도 생성했다.

- 변경 전후 현재·누적 HTML 바이트가 같았다. Excel 시트·셀·패키지는 생성/수정 시각 정규화 후 같았다.
- HTML과 Word/HWPX의 비어 있지 않은 표 셀은 현재 각각 134개, 누적 각각 268개로 내용이 일치했다(공백 정규화). 그림은 현재 2개, 누적 4개다.
- PDF는 현재 4쪽·그림 2개, 누적 8쪽·그림 4개다. 직접 PDF도 4쪽·그림 2개이며 3·4쪽의 스크리 그림·바이플롯·고유값 표를 렌더링해 확인했다.
