## 결과

현재 유효 캐시의 모듈 로딩 중앙값은 0.32초, 새 캐시 생성은 1.00초였다. 파일 변경 확인용 매니페스트 생성은 실행마다 한 번이며 약 0.03초였다. 반복 파일 검사를 생략하는 제품 변경을 도입할 근거는 이번 측정에서 찾지 못했다. 기존 로딩 정책을 유지했다.

## 조건

번들 R 4.5.3, JIT 3, UTF-8, 패키지 설치 검사 생략 조건이다. 미리 유효 캐시를 준비하고 hit/miss × 비계측/계측 × 새 프로세스 3회, 총 12개 프로세스를 순차 실행했다. miss는 매번 새로운 디렉터리를 사용했다. 다른 R 작업을 시간 측정과 동시에 실행하지 않았다.

모듈 로딩 뒤 서버 함수 생성, 초기 UI 구성 및 HTML 렌더링을 측정했다. 실제 브라우저 렌더링·Electron 실행·R 프로세스 시작·사용자 Shiny 세션 초기화는 포함하지 않는다. 운영체제 파일 캐시도 비우지 않았다. 따라서 설치 앱의 전체 콜드 스타트 시간이 아니다.

## 모듈 내부 계측

`app_module_cache_manifest`, `write_combined_app_module_cache`, `source_cached_app_modules`에 기록용 래퍼를 넣었다. 인수는 먼저 평가하고 원래 함수를 그대로 실행했다. 계측 실행 후 원래 함수를 복원했다.

- hit에서는 매니페스트와 캐시 읽기·평가 경로가 각각 한 번 호출됐다. 합친 소스 작성 함수는 호출되지 않았다.
- miss에서는 매니페스트, 합친 소스 작성, 파싱·평가·직렬화 캐시 생성 경로가 각각 한 번 호출됐다.
- 매니페스트는 hit 0.04/0.03/0.02초, miss 0.04/0.03/0.03초였다.
- hit의 `source_cached_app_modules`는 0.28/0.26/0.26초였다.
- miss의 합친 소스 작성은 0.07/0.08/0.08초, `source_cached_app_modules`는 0.88/0.88/0.85초였다.

마지막 경로는 miss일 때 파싱·평가·압축 저장을 모두 포함한다. 그 시간을 파일 읽기 또는 압축만의 비용이라고 단정할 수 없다. 계측 시간과 비계측 경과 시간을 섞어 정확한 분해나 예상 절감량을 계산하지 않는다.

캐시 유효성 확인은 오래된 코드의 재사용을 막는 데 필요하며 비용도 작다. 이전 실험에서 무압축 캐시는 파일 크기 증가에 비해 읽기 이득이 작아 선택하지 않았다. 후속 검토가 필요하다면 최초 생성 경로의 파싱·평가·압축 저장을 먼저 구분해야 한다. 무조건 선행 로딩하거나 파일 확인을 생략하는 변경은 하지 않았다.
