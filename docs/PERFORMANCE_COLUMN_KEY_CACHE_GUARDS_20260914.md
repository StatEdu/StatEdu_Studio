# 공통 열 이름 캐시의 실사용 보호 조건 검증 — 2026-09-14

## 결론

로케일·입력 형태·용량을 검사하는 공통 캐시 후보를 구현하고 측정했지만 **성능이 나빠져 채택하지 않았다**. 운영 파일은 작업 전과 바이트 단위로 동일하게 복원했다. 이전 단계의 한 번 렌더링 범위 시험에서 나타난 이득을 전역 캐시에 그대로 적용할 수 없음을 확인했다.

## 최종 후보의 시간

기존 혼합 반복측정 분석 결과(2,000행·4집단·6시점·공변량 1개)를 읽고 저장용 HTML만 생성했다. 번들 R 4.5.3, 한국어 설정, 독립 프로세스 3쌍, 두 번째 쌍 역순이며 측정은 순차 실행했다.

| 버전 | 최초 3회(초) | 반복 3회(초) | 최초 중앙값 | 반복 중앙값 |
|---|---|---|---:|---:|
| 기존 | 1.22, 1.17, 1.19 | 0.56, 0.53, 0.54 | 1.19 | 0.54 |
| 보호 조건 포함 캐시 | 1.24, 1.22, 1.22 | 0.60, 0.60, 0.61 | 1.22 | 0.60 |

반복 중앙값은 약 11.1% 증가했고 세 쌍 모두 기존보다 느렸다. 따라서 적용하지 않는 편이 낫다. 이 결과는 해당 후보와 워크로드에 관한 것이며 다른 방식의 열 단위 재사용까지 불가능하다는 의미는 아니다.

## 시험한 보호 조건

- 속성 없는 길이 1의 일반 문자열 중 128바이트 이하의 출력 가능한 ASCII만 재사용.
- Unicode, bytes 인코딩, 결측, 벡터, 이름/클래스 속성, 긴 문자열 등은 기존 변환 함수로 처리.
- `LC_CTYPE`가 바뀌면 캐시를 새로 생성. 소문자 변환과 영숫자 판정의 로케일 영향을 반영.
- 최대 256개로 제한하고 한도 도달 후 새 항목은 새 캐시에 저장.

단순 변환을 생략하는 이득보다 매 호출의 검사·조회 비용이 커졌다. 이전 시험은 렌더링마다 새 캐시를 사용했고 로케일 변경 검사를 하지 않았기 때문에 이번 후보와 같은 구현이 아니다.

## 동일성 확인

- C, English_United States.utf8, Korean_Korea.utf8 세 로케일에서 **7,338회** 값·경고/메시지·표준 출력 비교가 정확히 일치했다.
- 숫자·NULL·빈 값·결측·factor·named vector·matrix·사용자 정의 문자 변환·bytes 문자열·한글/Unicode·긴 문자열·새 열 이름 1,200개 및 반복 입력을 포함했다.
- 시험 환경에서 Turkish_Turkey.utf8는 설정할 수 없어 검증한 로케일에 포함하지 않았다.
- 각 로케일에서 캐시 크기는 256개 이하였다.
- 세 시간 측정 쌍의 전체 HTML·조건·표준 출력·난수 상태가 동일했고, 렌더링 전후 분석 객체도 동일했다.

## 다음 개선 방향

공통 함수에 전역 캐시를 두는 대신, **표를 생성할 때 열마다 정해지는 정보(열 분류·주석 열 여부·공통 스타일)를 한 번 계산해 행 반복에서 사용하는 방식**을 검토한다. 이 방식은 매 셀마다 캐시의 로케일·입력 조건을 확인하는 비용을 피할 여지가 있다. 아직 구현하거나 효과를 검증한 것은 아니다.
