# 빈도분석 캐시 메모리 구성·수명 검토 — 2026-09-14

현재 빈도분석 캐시를 점검했다. 20개 항목이 분석 결과 객체 하나를 공유했고, 12회 저장·반복 저장·초기화 과정에서 초기화 후 사용 중인 R 셀 수가 안정됐다. `object.size` 추정치를 실제 보관 메모리로 해석해 자료를 중복 제거하는 변경은 근거가 부족하므로 제품 코드는 변경하지 않았다.

## 세 지표의 구분

직전 적용에서 측정한 프로세스 최고 작업 집합은 291.5→311.4 MB로 약 19.9 MB 증가했다. 이 값은 패키지 로딩·분석·저장·검증 자료 기록을 포함하는 실행 전체의 최고치다. 아래 항목 추정 크기나 캐시 초기화 전후 사용 중인 R 객체 크기와 같은 지표가 아니다.

1. `object.size(entries)`는 현재 캐시의 바이트 한도 판단에 사용하는 보수적인 추정치다. 공유되는 객체도 각 항목에서 다시 합산될 수 있다.
2. `gc()`의 사용 중인 셀 수는 그 순간 R이 보관하는 객체를 측정한다. 힙 여유 공간·모든 네이티브 할당·Windows 작업 집합과 같지 않다.
3. `PeakWorkingSet64`는 전체 실행 중 프로세스 최고치다. 그것만으로 캐시의 지속 보관량이나 메모리 누수를 판정할 수 없다.

## 추정 크기 구성

번들 R 4.5.3, Windows, seed 714, 2,000행, 범주 4개·연속 4개, 20개 그림, 600 dpi를 사용했다. 캐시 항목 추정 크기는 14,051,208 bytes였다.

| 구성 요소 | 20개 항목에서 합산한 `object.size` |
|---|---:|
| PNG URI 문자열 | 890,264 bytes |
| 분석 결과 | 3,007,360 bytes |
| 실제 그리기 함수 | 4,165,920 bytes |
| 표시 문맥 | 5,913,600 bytes |
| 래퍼 함수 | 35,840 bytes |

이 표는 항목 내부를 구분해 합산한 값이며 목록·키 등의 오버헤드 때문에 합계가 전체와 정확히 일치하지 않는다. 또한 물리적인 개별 할당량을 나타내지 않는다.

`tracemem()`으로 원본 분석 결과와 20개 키가 참조하는 결과의 주소를 확인했다. 모두 같은 주소였다. 즉, 결과가 20개 별도 객체로 복제된 것은 아니다. 공유 확인은 분석 결과에 대해 수행했으며 함수·문맥 전체의 물리적 공유량까지 정량화하지는 않았다.

## 초기화 반복

20개 실제 PNG를 생성하고 같은 결과로 반복 저장한 뒤 캐시를 비우는 과정을 12회 실행했다. 각 회차는 결과 객체에 고유한 검사용 속성을 추가해 키를 바꿨다. 통계 데이터 자체를 바꾸는 시험은 아니다. 각 회차의 HTML은 캐시 없는 기준 HTML과 동일했고 첫 생성 RNG 상태도 같았으며, 반복 생성 HTML과 원본 분석 결과 직렬화 값도 유지됐다.

- 각 저장 후 항목 20개가 모두 현재 회차 결과를 가리켰다. 추정 크기는 검사용 속성을 포함해 14,054,568 bytes였다.
- 초기화 후 항목 0개, 빈 리스트 추정 크기 48 bytes였다.
- 초기화와 `gc()` 후 2~12회 모두 Ncells 1,739,416, Vcells 1,812,937로 일정했다. 측정 기록은 미리 할당한 행렬에 보관해 기록 자체의 증가를 피했다.

이 범위에서는 이전 결과·그림이 반복적으로 누적되는 증거가 없었다. 모든 장시간 세션에 누수가 없거나 OS에 메모리가 즉시 반환된다는 의미는 아니다.

## 사용 중인 R 객체의 차이

별도 프로세스에서 렌더링을 준비한 뒤 20개 그림을 캐시에 채우고 HTML 임시 결과를 버린 상태에서 `gc()`를 호출했다. 이어 캐시를 비우고 다시 측정했다. 2·3회 값은 다음과 같이 같았다.

| 상태 | 사용 Ncells | 사용 Vcells | `gc()`가 표시한 사용 메모리 합계 |
|---|---:|---:|---:|
| 캐시 보관 | 1,739,524 | 1,724,762 | 106.2 |
| 캐시 초기화 | 1,737,288 | 1,607,416 | 105.1 |

마지막 열은 `gc()`의 반올림된 `(Mb)` 열을 그대로 합산한 값이다. 차이는 약 1 MB 수준이며 OS 작업 집합 측정으로 환산하지 않았다. 이 결과는 14.05 MB 추정치나 19.9 MB 프로세스 최고치 차이를 지속 보관 메모리로 그대로 간주할 수 없음을 보여준다. 최고치 증가의 구체적인 할당 원인을 이번 검사만으로 확정하지는 않는다.

## 판단과 재현

기존 결과 공유와 초기화는 정상 동작했다. 단순히 크기 합산 방식을 바꿔 숫자를 줄이는 것은 실제 메모리 개선이 아니며 보관 한도를 느슨하게 만들 수 있다. 이번에는 16 MiB 추정 한도와 캐시 동작을 유지했다. 제품 출력 변경이 없어 5종 변환과 설치 빌드는 재실행하지 않았다.
