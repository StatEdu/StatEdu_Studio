# 현재 PLS 부트스트랩 단계별 기준 측정

실행 코드를 바꾸지 않고 `structural_canvas_run_plsc_bootstrap()`의 현재 비용을 측정했다. 기존 자동 병렬 경로가 이 작은 모형에서 직렬보다 빠르게 작동함을 확인했다. 새로운 최적화의 개선율이 아니다.

## 입력과 실행

`scripts/validate_pls_bootstrap_parallel_reproducibility.R`의 실행 전 fixture를 그대로 재사용했다. 120행, A/B/C 3개 구성개념, 각각 3개 지표, A→B/A→C/B→C 모형이다. 완전자료, mode A composite PLS이며 PLSc·잠재 조절은 포함하지 않는다. 데이터 seed 20260901, 부트스트랩 seed 24680, 500회다. 기존 5,000회 성능이나 큰 모형 성능으로 환산하지 않는다.

번들 Windows R 4.5.3, seminr 및 현재 PLS 소스를 사용했다. 독립 프로세스 3개를 순차 실행했다. 각 프로세스에서 원본 직렬 호출로 기준 결과를 만든 뒤, 계측 사본의 직렬 및 자동 설정을 실행했다. 두 번째 프로세스에서는 자동 설정을 먼저 실행했다. 자동 설정은 작업자 8개, batch 400; 직렬은 작업자 1개, batch 100이었다. 설정은 측정 프로세스 안에서만 변경했다.

계측 사본은 AST의 최상위 단계 경계에 시각 기록 3개만 삽입했다. 원본 함수를 덮어쓰거나 패키지 namespace를 수정하지 않았다. 준비 단계는 첫 계측 호출의 컴파일 영향을 포함할 수 있다. 이 측정은 엄격한 첫 호출 A/B 최적화 실험이 아니다.

## 경과 시간

|설정|1회|2회|3회|중앙값|
|---|---:|---:|---:|---:|
|직렬 전체|2.38|2.30|2.32|2.32초|
|자동 병렬 전체|0.72|0.79|0.72|0.72초|

|단계|직렬 중앙값|자동 병렬 중앙값|
|---|---:|---:|
|기준 통계·난수 스트림 등 준비|0.07|0.02|
|PSOCK 작업자 생성 및 자료 전송|0.00|0.26|
|재표집·적합·유효성 검사·배치 통신/수집|2.28|0.42|
|최종 요약·작업자 종료·캡처 마무리|0.01|0.03|

단위는 초다. 단계별 중앙값 합은 전체 중앙값과 같을 필요가 없다. 재표집 단계에는 배치 전송/결과 수집이 포함되어 순수 적합 CPU 시간과 같지 않다. 마지막 단계에는 `on.exit(stopCluster())` 및 결과 캡처 종료가 포함된다. 직렬 작업자 생성 0은 해당 경로가 없다는 뜻이며 일반적인 함수 비용 0을 주장하지 않는다.

제외 범위: fixture 생성과 초기 적합, 패키지 로딩, 앱의 외부 `callr::r_bg` 생성, 모델 RDS 저장·로드, 진행 파일 I/O(`progress_file=NULL` 사용), 최종 작업 결과 RDS 저장, UI 렌더링. 따라서 실제 앱에서 누른 순간부터 결과 표시까지의 시간은 아직 별도 측정이 필요하다.

## 결과 검증과 진단의 범위

원본 직렬 3개, 계측 직렬 3개, 계측 자동 3개의 **전체 반환 객체 및 부모 RNG**가 `identical(..., num.eq=FALSE)`로 정확히 같았다. 모든 결과가 요청 500회/유효 500회이고, 반환 객체에 포함된 유효 위치·원시 추정 배열·최종 요약을 함께 비교했다. 재표집 행 인덱스를 별도로 추출·비교한 것은 아니다.

직렬에서는 원본/계측의 경고·메시지·표준 출력까지 정확히 같았다. 각 직렬 캡처에는 1,000개의 경고/메시지 조건이 있었고 표준 출력은 0줄이었다. 자동 병렬의 부모 캡처는 조건 0개, 출력 0줄이다. 작업자 내부 진단이 부모 핸들러로 전달되지 않는 기존 실행 구조 때문에 **직렬/병렬의 진단까지 동일하다고 주장하지 않는다.** 이번에 경고를 새로 없애거나 경로를 변경하지 않았다.

## 별도 직렬 프로파일

세 번째 프로세스에서 준비와 `gc()`를 마친 뒤 별도의 직렬 500회를 10ms Rprof로 측정했다. 프로파일 실행 전체 결과·진단·출력·RNG도 원본 기준과 정확히 일치했다. 154개 샘플(표본 시간 1.54초)의 포함 스택 비중은 다음과 같다.

- `seminr::estimate_pls`: 약 63.0%
- `seminr:::HTMT`: 약 22.1%
- `as.matrix.data.frame`: 약 16.2%
- `scale.default`: 약 29.2%

서로 중첩되는 호출 비중이며 더하면 안 된다. 부모 프로세스의 직렬 프로파일이므로 병렬 작업자 CPU 분포를 직접 측정한 것은 아니다. 단일 소규모 프로파일의 비중을 일반화하지 않는다.

다음 국소 검토는 반복 적합과 HTMT 내부의 행렬 변환·표준화 준비가 중복되는지 확인하는 것이다. 재표집마다 자료가 달라지므로 통계량을 다른 반복 사이에서 재사용하거나 유효성 검사를 없애지 않는다. 실제 앱 경로 및 5,000회 조건은 별도 후속 측정 대상으로 남긴다.
