# Light's kappa 범주 코드 재사용 검토: 미적용

## 결론

Light's kappa에서 평가자 쌍마다 factor 변환을 반복하는 대신 평가자 열별 범주 코드를 한 번 생성하는 후보를 시험했다. 원시 Light 계수·진단·출력·RNG 비교 100건과 전체 분석 비교는 통과했으나 결측 자료의 전체 실행이 세 번 중 두 번 느려져 적용하지 않았다.

제품 파일은 변경하지 않았다. 제품과 시작 스냅샷의 SHA256은 `8391EC42E1F8D2ED44243E4F1B61041C5AA3135E1982615C7FB8A3482FD6CABA`로 일치한다. 이전 ICC·Gwet·Krippendorff 개선은 유지한다.

## 후보

일반 data.frame의 모든 열이 plain character이며 levels가 중복/NA 없는 일반 문자 벡터일 때만 열별 factor 정수 코드를 미리 만든다. 범주 수가 2 이상이고 교차표 크기가 integer 범위를 넘지 않는 조건도 확인한다. factor·숫자·사용자 클래스·잘못된 levels 등은 원래 함수로 처리한다.

각 쌍의 교차표는 기존과 같은 열 우선 셀 코드 및 tabulate로 생성한다. 원래 Cohen kappa 함수에서 교차표 이후 산식을 추출해 그대로 실행하며, 쌍 순서와 최종 mean 계산은 유지한다. 코드는 시험용 지역 환경에만 설치했다. 패키지 namespace나 제품은 수정하지 않았다.

일반 화면의 명목형 다평가자 분석은 Light kappa에 완전 사례만 전달한다. 따라서 전체 자료의 결측률이 높으면 Light에 들어가는 행 수가 줄어 사전 변환 비용 감소의 이득도 제한될 수 있다. 이번 시간 차이의 원인을 이 설명만으로 단정하지는 않는다.

## 전체 분석 시간

번들 R 4.5.3, 자료 seed 939, 5,000행·8평가자·5범주, 명목형 전체 분석이다. 결측 없음과 별도 난수 마스크의 결측 생성 확률 1/6을 비교했다. 독립 프로세스 3개를 순차 실행하고 워밍업 후 두 번째는 후보부터 측정했다. 로딩을 제외하고 전체 결과 캡처를 포함한다.

| 결측 생성 확률 | 현재 1 / 2 / 3 (초) | 후보 1 / 2 / 3 (초) | 중앙값 |
|---|---|---|---|
| 0% | 0.18 / 0.11 / 0.19 | 0.11 / 0.19 / 0.10 | 0.18 → 0.11 |
| 약 17% | 0.11 / 0.14 / 0.12 | 0.14 / 0.12 / 0.16 | 0.12 → 0.14 |

완전 자료에서는 두 번 빨라졌으나 두 번째 실행은 느려졌다. 결측 자료는 두 번 느려지고 중앙값도 증가했다. 이 결과로 공통 경로를 변경할 만큼 안정적인 이득이 확인됐다고 판단하지 않았다. 짧은 실행의 변동과 두 자료 조건의 제한을 고려해야 한다.

각 워밍업과 측정에서 전체 반환 객체·조건 클래스/본문/순서·표준 출력·RNG가 `identical(..., num.eq=FALSE)`로 일치했다. 같은 두 자료 조건의 반복 비교이며 모든 입력에 대한 보장은 아니다.

## 원시 검증

평가자 수 2/3/8/20 × 일반 결측 자료/빈 자료/상수/factor/숫자 × 기본 levels/역순/관측값 일부 미등록/중복 levels/NA levels의 100개 조합을 비교했다. 원시 Light kappa와 조건·표준 출력·RNG가 허용오차나 정규화 없이 일치했다. 오류 반환 조건도 포함하며 성공 추정치 100개로 해석하지 않는다. 모든 개별 쌍의 교차표와 Cohen kappa를 따로 수집한 검증은 아니다.
