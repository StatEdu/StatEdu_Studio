# Fine–Gray 네이티브 후보 극단 입력·메모리 검증 — 2026-09-14

## 결과

설치 cmprsk 2.2-12, 같은 소스를 재빌드한 원본, 캐시 후보를 추가 100조건에서 비교했다. 전체 반환값·오류/경고/메시지·표준출력·난수 상태·분산 루틴 호출 수가 `identical(..., num.eq=FALSE)`로 일치했다. 운영 소스와 설치 DLL을 변경하지 않았고 설치 파일도 재빌드하지 않았다.

## 입력과 검증 범위

80행·3공변량, 시드 44 자료에 다음 10조건을 적용했다: 일반, 동률 시간, 전원 검열, 전원 관심 사건, 관심 사건 없음, 모든 시간 0, 시간 1e200 배율, 공변량 1e-150 배율, 공변량 1e150 배율, 상수열. 각각 초기 계수 0/1/-1/1000/-1000과 `maxiter=0/10`을 조합했다. 시간가변 공변량은 이번 검사에 포함하지 않았으며 이전 직접 적합 검증에서 원본 경로 복귀를 검사했다.

- 100조건 모두 동일했다.
- 분산 루틴 `crrvv` 호출까지 도달한 조건은 65건이다. 호출 진입을 센 것이며 65건 모두 분산 계산에 성공했다는 의미는 아니다.
- 정상 반환 42건: 수렴 25건, 미수렴 17건.
- 오류 58건: 특이 행렬 오류 26건, 논리 조건의 결측값 오류 32건. 오류 메시지도 일치했다.

시험용 `.Fortran` 래퍼로 분산 호출 진입을 기록했다. 모든 극단 입력이 캐시를 실행한 것은 아니므로 100건 전체를 캐시 경로의 성공 검증으로 해석하면 안 된다. 원래 구현보다 지수값을 일찍 계산하면서 생길 수 있는 하드웨어 부동소수점 상태 플래그 차이는 검사하지 않았다.

## 메모리

2,000행·10공변량 직접 `crr()` 적합을 설치/후보 각각 새 프로세스에서 3회 실행하고 두 번째 묶음은 순서를 반대로 했다. `Sys.getpid()`가 기록한 실제 R 계산 프로세스를 Windows에서 약 20ms 간격으로 추적하여 `PeakWorkingSet64`의 최대 관측값을 수집했다. 입력 생성·DLL 로딩·적합·결과 저장을 포함한 프로세스 메모리이며 네이티브 캐시만의 할당량은 아니다. 실행 시간 벤치마크와 분리했다.

| 묶음 | 설치 버전(바이트) | 후보(바이트) |
|---|---:|---:|
| 1 | 179,556,352 | 179,949,568 |
| 2 | 179,920,896 | 179,548,160 |
| 3 | 180,105,216 | 179,982,336 |
| 중앙값 | 179,920,896 | 179,949,568 |

중앙값 차이는 28,672바이트(약 0.016%)로 이 측정에서 의미 있는 메모리 증가를 확인하지 못했다. 소스의 추가 double 배열은 이 입력에서 16,000바이트다. 프로세스 작업 집합은 전체 할당량·최대 커밋 메모리와 다르며 종료 직전 표본을 놓칠 수 있다. 큰 표본 크기의 메모리는 아직 측정하지 않았다. 측정 결과 3쌍도 전체 결과·진단·표준출력·난수 상태가 동일했다.

최초 측정은 Windows 실행기만 추적하여 약 8.3MB를 반환했기 때문에 폐기했다. `launcher-only-invalid.csv`는 그 잘못된 측정이며 결과에 사용하지 않는다. 수정된 측정은 R이 직접 기록한 PID를 사용한다.
