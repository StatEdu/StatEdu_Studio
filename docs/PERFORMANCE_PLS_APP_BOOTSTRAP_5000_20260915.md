# PLS 5,000회 실제 백그라운드 작업 경로 기준 측정

`structural_canvas_start_pls_bootstrap_job()`을 그대로 호출해 외부 callr 작업 시작, 모델 저장/로드, 내부 PSOCK 재표집, 진행 파일 기록, 결과 저장 및 부모의 결과 읽기를 측정했다. 제품 코드는 변경하지 않았다. 이 결과는 새 최적화의 개선율이 아니라 현재 경로의 기준값이다.

## 조건

- 번들 Windows R 4.5.3 및 현재 PLS 엔진.
- 기존 병렬 재현성 fixture: 120행, 3개 구성개념, 각각 3개 지표, A→B/A→C/B→C, 완전자료 composite PLS. PLSc·고차 구성개념·잠재 조절은 포함하지 않는다.
- fixture seed 20260901, 부트스트랩 seed 24680, 요청 5,000회. 실제 작업 함수의 자동 작업자 설정을 유지했다. 진행 기록에서 batch 400을 확인했다(현재 자동 최대 8개 작업자의 batch 규칙).
- 독립 부모 R 프로세스 3개를 순차 실행했다. 각 실행에서 새 callr 작업과 내부 작업자들이 생성됐다. 초기 데이터 생성 및 점추정 적합은 타이머 밖이다.
- 부모는 진행 파일과 작업 생존 상태를 약 50ms마다 확인했다. 파일 갱신을 모두 포착한다고 보장할 수 없고, 관측 시간은 폴링 지연을 포함한다.

첫 샌드박스 실행은 processx 통신 파이프 생성 단계에서 접근 거부로 시작하지 못했다. 이 실패는 시간 표에 넣지 않았다. 같은 명령을 승인된 제한 밖 로컬 실행으로 다시 실행해 3회를 완료했다. 제품의 작업 시작 방식을 우회하거나 직렬 경로로 대체하지 않았다.

## 시간

작업 시작 함수 호출 직전부터의 경과 시간(초):

|관측 지점|1회|2회|3회|중앙값|
|---|---:|---:|---:|---:|
|작업 시작 함수 반환|0.34|0.33|0.33|0.33|
|첫 resampling 상태 관측|0.89|0.88|0.94|0.89|
|결과 파일 존재 첫 관측|4.76|4.88|4.75|4.76|
|작업 종료 확인 및 결과 읽기 완료|4.76|4.88|4.81|4.81|

파일 존재만으로 읽기 가능 여부를 판정하지 않았다. 작업 종료와 종료 코드 0을 확인한 뒤 결과 RDS를 읽고 성공 출력을 검증했다. 각 단계의 중앙값을 빼서 정확한 내부 비용으로 해석하지 않는다. 첫 resampling 관측 전에는 외부 프로세스 시작·소스 로딩·모델 읽기·내부 작업자 준비가 함께 포함된다.

**제외 범위:** 앱 자체 로딩, 사용자 클릭/이벤트 대기, 분석 전 점추정, Shiny 폴링 및 반응형 처리, 결과표·그래프 렌더링과 내보내기. 따라서 4.81초를 사용자가 클릭한 순간부터 화면 표시 완료까지의 시간으로 부르면 안 된다. 다음 전체 사용자 대기시간 측정에는 화면 준비 완료 지점이 필요하다.

## 정확성 및 한계

각 실행에서 요청 5,000회, 유효 5,000회, 유효 위치 `seq_len(5000L)`, 정상 자식 종료를 확인했다. 저장한 전체 반환 객체와 부모 RNG 상태는 세 실행 간 `identical(..., num.eq=FALSE)`로 정확히 같았다. 수치·속성·유효 마스크·반환 추정 배열·최종 요약을 정규화하거나 반올림하지 않았다.

이는 동일 설정의 반복 재현성 검증이며 이전 버전 또는 직렬 5,000회와의 A/B 비교는 아니다. 자식 프로세스의 모든 경고/메시지와 내부 RNG를 캡처한 검사는 아니므로 이들까지 동일하다고 주장하지 않는다. 시간과 진행 갱신 시각은 비교 대상 통계 결과와 별도로 기록했다.

500회 내부 함수의 앞선 0.72초와 직접 비율 비교하지 않는다. 이번에는 반복 수와 외부 작업/파일 I/O 측정 범위가 다르다. 8월 다른 감사의 5,000회 기록과도 fixture 및 버전·환경을 맞추지 않았으므로 개선율을 계산하지 않는다.
