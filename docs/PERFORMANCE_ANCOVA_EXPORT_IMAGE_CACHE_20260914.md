# 공분산분석 저장 그림 재사용 — 2026-09-14

## 적용 결과

공분산분석의 HTML/PDF/Excel 저장 버튼이 세션 내 동일한 분석 결과의 PNG를 재사용하도록 변경했다. 관측치 2,000개, 결과 변수 4개, 그림 20개 조건에서 반복 저장용 HTML 생성 중앙값은 **4.47초 → 0.52초(약 88.4% 감소)**였다. 최초 생성은 **5.11초 → 5.32초(0.21초 증가)**였다.

분석 계산과 그림 그리는 수식·함수는 유지했다. 선형성 진단에서는 매번 만들던 익명 함수를 없애고 기존 그림 함수에 공변량 식별자를 포함한 결과를 직접 전달한다. 이 방식으로 공변량별 그림을 정확히 구별하면서 같은 그림을 재사용한다.

## 변경 범위와 제한

- `R/result_ancova_ui.R`: 그림 생성 함수를 선택적으로 전달하고, 선형성 진단에 명시적인 결과 입력을 사용한다. 기본 동작은 기존 PNG 생성이다.
- `R/result_saved_ui.R`, `R/result_export.R`: 선택적 `plot_renderer`를 HTML/PDF/Excel 저장 경로로 전달한다.
- `R/server_ancova.R`: 공분산분석 세션 전용 캐시를 만들고 저장 버튼들이 공유한다. 분석 결과 변경·NULL 초기화·세션 종료 시 해제한다.
- 공통 캐시의 결과·그림 함수·크기·해상도·옵션·로케일 등 동일성 검사를 유지한다. 경고/메시지 또는 난수 상태 변경이 있는 생성은 캐시하지 않는다.
- FIFO 최대 32개, `object.size` 기준 48 MiB 제한이다. 한도를 넘는 항목은 기존 생성 경로로 처리한다. 이 제한은 실제 프로세스 메모리 상한이 아니다.
- 화면의 최초 그림 생성과 개별 그림 파일 저장에는 기존 기본 렌더러가 적용된다. 누적 결과 변환은 저장된 스냅샷을 사용한다.

## 성능 검증

번들 R 4.5.3, 기존 앱 부트스트랩, 그림 설정 600 DPI. 집단 4개·연속 공변량 2개이며 결과 변수마다 보정평균/원자료 중첩/회귀선/선형성 진단 2개를 표시했다. PNG 크기는 기존과 같은 3,400 × 2,500이다. 분석 완료 후 저장용 HTML 생성만 측정했으므로 앱 시작, 분석, PDF/문서 변환 시간은 포함하지 않는다.

조건별 독립 프로세스 3회, 두 번째 쌍 역순. 측정 작업끼리 동시에 실행하지 않았으며 CSS는 고정했다. 메모리는 별도 프로세스 3쌍에서 측정했다.

| 버전 | 최초 3회(초) | 반복 3회(초) | 최초 중앙값 | 반복 중앙값 |
|---|---|---|---:|---:|
| 변경 전 | 5.17, 5.11, 5.09 | 4.49, 4.47, 4.47 | 5.11 | 4.47 |
| 변경 후 | 5.32, 5.36, 5.28 | 0.53, 0.52, 0.51 | 5.32 | 0.52 |

변경 후 각 실행에서 최초·반복 합계 PNG 렌더 횟수는 **20회**였다. 캐시 항목의 `object.size` 합계는 **36,097,056 bytes**였다. 이 값은 공유 객체나 함수·환경을 포함하는 R 추정치이며 실제 추가 할당량으로 해석하지 않는다.

실제 R 계산 PID의 Windows `PeakWorkingSet64`:

| 버전 | 1회(bytes) | 2회(bytes) | 3회(bytes) | 중앙값(bytes) |
|---|---:|---:|---:|---:|
| 변경 전 | 361,148,416 | 360,656,896 | 371,060,736 | 361,148,416 |
| 변경 후 | 350,113,792 | 350,662,656 | 351,096,832 | 350,662,656 |

이 워크로드에서는 최대 작업 집합 중앙값이 약 10.49 MB 낮았다. 반복 PNG 생성의 임시 메모리를 피한 효과가 포함될 수 있으며, 모든 데이터에서 메모리가 줄어든다는 보장은 아니다. 캐시는 결과를 유지하는 비용이 있고, 다른 크기·설정에서는 적중률이 달라질 수 있다.

초기 16 MiB와 32 MiB 후보는 20개 그림을 모두 유지하지 못해 반복 저장에서도 총 40회 렌더가 발생했다. 이 후보들은 채택하지 않았고 별도 `excluded-16mb`, `excluded-32mb`에 보존했다. 32 MiB 후보 마지막 회차에는 진단 R 실행이 겹쳤으므로 최종 성능 근거로 사용하지 않았다. 위 표는 최종 48 MiB 구현을 새로 단독 측정한 결과다.

## 동일성·수명·저장 검증

- 3쌍 시간 측정과 3쌍 메모리 측정에서 변경 전후 HTML 전체, 모든 내장 PNG, 경고·메시지·표준 출력·난수 상태가 정확히 일치했다. 각 실행의 최초/반복 출력도 동일했다.
- 렌더링 전후 분석 결과 스냅샷 동일성 확인. 검증용 복제본에서만 lm 잔차·적합값 이름을 일반 문자열로 정규화해 R 지연 문자열 표현 차이를 제거했다.
- 12개 표시 사례: 기본, 반복, 보고서, CSS, 소수점, 언어, 변수 라벨, 300 DPI, 순위 ANCOVA, 결측, 범주형 공변량, 그림 없음. 변경 전후 전체 출력 동일.
- 실제 ANCOVA 서버 핸들러: HTML 2회/PDF/Excel에서 5개 PNG만 생성. 결과 변경, 실제 초기화 입력, 항목이 채워진 세션 종료 시 캐시 해제.
- 1-byte 한도의 실제 PNG 우회 시험: 재사용 없이 10회 생성하고도 두 출력과 기본 렌더 출력이 동일.
- `scripts/validate_ancova_export_image_cache.R`: 공변량별 안정적인 키, 결과/컨텍스트 무효화, 해제 통과.
- `scripts/validate_correlation_export_image_cache.R`: 공통 캐시의 FIFO·함수/인자/환경 변경·세션 격리·용량·경고/메시지/난수/오류 우회 검증 통과.
- 실제 직접 HTML/PDF/Excel 작성기에서도 5개 PNG만 생성했다.

현재 및 누적 결과의 HTML/PDF/Word/HWPX/Excel, 총 10개 파일을 실제 생성했다. 변경 전후 현재·누적 HTML과 Excel 패키지는 동일했다(Excel 생성/수정 시간 제외). Word/HWPX는 HTML의 비어 있지 않은 표 셀 전체와 그림 개수를 비교했다. PDF 그림 개수와 페이지를 확인하고 직접 저장 PDF의 그림 5개를 시각적으로 점검했다.

| 범위 | HTML/Word/HWPX 비어 있지 않은 표 셀 | 그림 | PDF 페이지 |
|---|---:|---:|---:|
| 현재 | 235 | 5 | 9 |
| 누적(동일 결과 2개) | 470 | 10 | 18 |

표시 내용의 변경 전후 동일성은 전체 HTML/PNG 비교가 근거이며, 서로 다른 파일 형식의 바이너리 동일성을 주장하는 것은 아니다.

## 기존 종합 테스트 정리

기존 `scripts/validate_ancova.R`는 ‘Analysis method 설명이 ES 정의보다 먼저’라는 오래된 순서 검사에서 실패했다. 변경 전 UI/저장/서버 코드를 복원한 시험에서도 동일한 첫 실패를 재현했다. `AGENTS.md`와 `docs/table_output_rules.md`의 현행 규칙인 ‘정의가 설명보다 먼저’에 맞춰 일반·혼합 결과의 검사 두 곳만 수정했다. 운영 주석은 변경하지 않았다.

수정 후 실제 Chrome PDF 저장을 포함한 종합 테스트가 **All ANCOVA validations passed**로 완료됐다. 제한 환경의 Chrome 실행 실패는 기존과 같은 외부 브라우저 권한 문제였고, 허용된 실행으로 재검증했다. 이번 변경 파일의 `git diff --check`도 통과했다.
