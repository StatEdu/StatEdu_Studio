# 현재 모듈 로딩과 첫 Kendall 실행 재측정

## 결과

최근 분석 변경이 반영된 현재 프로그램에서 모듈 캐시 재사용이 미사용보다 빨랐다. 모듈 로딩 중앙값은 유효 캐시 재사용 0.32초, 최초 캐시 생성 0.86초, 캐시 미사용 0.64초였다. 캐시 방식에 따른 분석 결과 차이는 없었다. 이번 작업은 현재 상태의 측정이며 제품 코드를 변경하지 않았다.

| 모듈 캐시 | 패키지 로딩 중앙값 | 모듈 로딩 중앙값 | 첫 Kendall 중앙값 | 두 번째 Kendall 중앙값 |
|---|---:|---:|---:|---:|
| 재사용 | 0.25 | 0.32 | 0.27 | 0.03 |
| 최초 생성 | 0.25 | 0.86 | 0.28 | 0.05 |
| 미사용 | 0.25 | 0.64 | 0.27 | 0.03 |

단위는 초다. bootstrap 소스 읽기는 측정 해상도에서 0초로 표시됐으며 실제 비용이 없다는 뜻은 아니다. 기존 날짜의 다른 소스 측정과 비교해 회귀나 추가 개선율을 주장하지 않는다.

## 방법과 범위

번들 Windows R 4.5.3, JIT 3, 영어 UTF-8, 패키지 설치 검사 생략 환경이다. 재사용용 캐시를 별도 준비 프로세스에서 만들고 hit/miss/off를 각각 새 R 프로세스 세 개에서 순차 실행했다. miss는 실행마다 새 디렉터리이며 기존 사용자 캐시를 삭제하거나 수정하지 않았다. 운영체제 파일 캐시는 비우지 않았다.

패키지 로딩, 모듈 로딩, 첫 분석, 두 번째 분석을 각각 측정했다. Kendall 분석은 시드 33의 반올림한 정규 자료 2,000행·6변수·15쌍, 정규성 및 잠재상관 비활성화 조건이다. 분석 시간에는 결과·진단·stdout·난수 수집이 포함된다. 자료 생성은 분석 시간에서 제외한다.

이 측정에는 Electron 실행, R 프로세스 생성, 실제 Shiny 서버 세션 초기화, UI 구성·브라우저 렌더링·내보내기가 포함되지 않는다. 따라서 표의 단계나 그 합계를 설치 앱 전체의 시작 시간이라고 부르지 않는다.

## 관측과 후속 검토 범위

모듈 로딩 원자료는 재사용 0.32/0.31/0.32초, 최초 생성 0.86/0.86/0.87초, 미사용 0.64/0.65/0.64초였다. 기존 식 캐시의 재사용 및 gzip 수준 1 기록 정책을 유지한다. 이 측정에서는 반복 파일 읽기를 추가로 줄이는 변경을 도출하지 않았다.

첫 Kendall 실행은 0.25~0.28초, 두 번째 실행은 0.03~0.05초였다. 최초 엔진 생성, 함수 첫 호출 컴파일, 기타 초기화가 후보 원인이지만 이번에는 각각의 비용을 계측하지 않았다. 이 차이 전체를 Kendall 엔진이나 JIT의 비용으로 단정하지 않는다. 다음 검토에서는 실제 첫 호출 경로를 분리해 확인할 필요가 있다.

## 결과 보존

각 프로세스의 첫/두 번째 분석 결과가 정확히 같았으며, 9개 프로세스의 전체 반환값·경고/메시지·stdout·난수 상태도 서로 일치했다. 세 최초 생성 캐시에서 읽은 버전·매니페스트·식 객체는 재사용 캐시의 전체 객체와 일치했다.

모든 비교는 `identical(..., num.eq=FALSE)`이며 결과 수치나 HTML의 정규화·반올림·허용오차를 사용하지 않았다. HTML은 이번 검증에서 생성하지 않았다. 캐시 간 비교가 모든 분석 종류의 동일성을 입증하는 것은 아니며 이번에 실행한 Kendall 결과를 대상으로 한다.

## 자료

`output/startup-kendall-current-20260915/`의 bootstrap.R, measure.R, compare.R, 실행별 CSV/RDS, timings.csv, summary.csv, 전용 cache-hit/cache-miss 디렉터리에 자료를 보존했다. miss 실험을 다시 실행하려면 기존 폴더를 덮어쓰지 않고 새 실행 번호를 사용해야 한다. 캐시의 매니페스트와 합친 소스에 당시 모듈 입력이 기록돼 있다.

제품 bootstrap 소스가 저장한 스냅샷과 같은 해시임을 확인했다. 출력 코드 변경·내보내기 생성·배포 빌드는 수행하지 않았다.
