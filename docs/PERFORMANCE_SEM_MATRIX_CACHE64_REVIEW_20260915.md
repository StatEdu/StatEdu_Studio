# SEM 역행렬 갱신 64개 캐시 후보 — 미반영

앞선 동일 입력 호출 감사에서 찾은 중복을 실제로 재사용하는 후보를 시험했다. **9개 비교 모두 느려져 제품에 적용하지 않았다.** 원 계산이 중복된다는 사실만으로 캐시가 더 빠르지는 않았다.

## 후보

한 재적합 호출마다 새로 생성하는 64항목 LRU 캐시를 연구용 프로세스에 설치했다. 숫자형 일반 행렬과 속성 없는 정수 삭제 인덱스에 한정하고, 비유한 행렬/NA 인덱스 등은 원 계산으로 보냈다. s_inv, rm_idx, logdet, s_logdet 전체의 xxhash64로 조회한 뒤 `identical(..., num.eq=FALSE)`로 인자 동일성을 다시 확인했다. 값의 반올림이나 근사 비교는 사용하지 않았다. 경고·메시지를 낸 계산은 저장하지 않고 오류는 그대로 전파했다.

적합 사이에는 캐시를 공유하지 않았다. 연구용 R의 lavaan namespace 함수 바인딩만 잠시 감싼 뒤 원 함수로 복구하고 복구 동일성을 검사했다. 제품 및 설치된 패키지 파일은 변경하지 않았다. 해시 조회·정확 비교·항목 저장·LRU 순서 갱신 비용과 각 적합의 캐시 초기화 비용을 모두 포함했다.

## 측정

앞선 감사와 같은 240행/9지표/10% 결측 일반 SEM의 저장된 재표집 인덱스 첫 3개를 사용했다. 각 표본을 직접 직렬로 재적합했다. 새 R 프로세스 3개에서 기준/후보 각각 준비 실행 후, 5회 묶음의 적합 및 결과 캡처/동일성 검사 시간을 측정했다. 두 번째 프로세스는 후보를 먼저 실행했다. 표의 시간은 블록 경과 시간을 5로 나눈 값의 3프로세스 중앙값이다.

|재표집|기준|후보|
|---|---:|---:|
|1|0.156초|0.204초|
|2|0.162초|0.214초|
|3|0.174초|0.200초|

3표본 × 3프로세스 모두 후보가 느렸다. 이 구현에서는 계산 절감보다 조회/비교/저장 및 래퍼 비용이 더 컸다. 다른 캐시 구현이나 다른 행렬 크기도 모두 느리다는 결론은 아니다. 전체 200/5,000회 병렬 부트스트랩 시간으로 환산하지 않는다.

별도 적중 확인에서는 첫 표본의 전체 2,812호출 중 원 함수 계산 2,432회, 실제 캐시 적중 380회를 확인했다. 적중이 없어 느린 것이 아니었다. 이 계수 계측은 위 성능 측정과 분리했다.

## 결과 보존 검증 범위

파라미터 표, 표준화 추정표, vcov, 수렴 상태, 적합 중 경고·메시지·표준 출력 및 최종 부모 RNG가 계측/후보 실행과 기준 사이에 `identical(..., num.eq=FALSE)`로 일치했다. 별도 적중 검사에서도 같은 비교를 통과했다. 전체 lavaan S4 객체 및 전체 부트스트랩 요약의 동일성 검사는 아니다.

성능 기준에서 이득이 없어 제품 채택을 보류했으므로 logdet 특수 값, 모든 삭제 인덱스/사용자 정의 클래스, 모든 경고·오류 분기의 확대 검증과 병렬 적용 검증은 진행하지 않았다. 이번 fixture의 결과 일치를 모든 입력에 대한 검증으로 표현하지 않는다.
