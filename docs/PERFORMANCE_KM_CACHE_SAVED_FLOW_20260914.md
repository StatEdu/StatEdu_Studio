# KM 캐시의 저장 HTML 통합 실험 — 2026-09-14

후속 상태: 메시지 발생 시 그래픽 장치 상태가 달라지는 것을 확인하여 이 후보를 제품 적용 대상에서 제외했다. 속도와 HTML 동일성 측정은 유효하지만 전체 동작 보존을 뜻하지 않는다. `PERFORMANCE_KM_CACHE_MESSAGE_CONTEXT_20260914.md` 참고.

## 결과

검증용 캐시를 KM 저장 HTML 흐름의 메모리 복사본에 연결했다. 8개 그림을 포함한 HTML의 반복 생성은 중앙값 0.25초였고, 캐시 없이 새로 생성하면 8.88초였다. HTML·이미지 URI·메시지 조건 정보·난수 상태를 정확히 보존했다. 제품 저장 버튼에는 아직 연결하지 않았다.

## 통합 중 발견·수정한 문제

초기 후보는 테마와 요소 트리를 각 그림 키에 중복 포함했다. `object.size()` 기준 환경 정보가 약 47.84MB여서 64MiB 상한에 그림 하나만 남았고, 8개를 순서대로 저장하면 이전 그림이 계속 밀려나 반복 저장에서도 캐시가 적중하지 않았다. 초기 3개 실행의 예상 렌더 횟수 검사가 실패했으며 성공 수치에 포함하지 않았다.

`output/km-image-cache-candidate-20260914/cache.R`을 수정했다. 환경 정보를 캐시 전체에 한 번만 저장하고 환경이 달라지면 모든 항목을 비운다. 항목과 공유 환경의 합산 `object.size()`를 용량 제한에 반영한다. clear는 둘 다 비우며, 보관된 그림이 없으면 환경 정보도 해제한다. 기본 후보 경계 검사를 다시 통과했다.

이 값은 객체 크기 계산치이며 실제 프로세스 메모리 증가나 최대 RSS 측정치가 아니다. 객체 그래프의 공유 참조 때문에 계산치와 실제 메모리는 다를 수 있다. 최종 8개 그림 항목의 합산 크기는 약 2.18MB였고 공유 환경과 합쳐 설정한 64MiB 안에 남았다. 본 실험은 64MiB/16항목을 명시적으로 지정했다. 후보의 기본 16MiB 설정으로 이 환경이 들어간다고 주장하지 않는다.

## 측정

번들 R 4.5.3, JIT 3, 새 프로세스 3개를 순차 실행했다. 기존 KM 객체에 4종 곡선 × 색상/흑백을 지정했다. 그림 명세에 결과·종류·버전·언어를 붙이고, HTML 삽입 함수 복사본이 안정적인 캐시 렌더러를 호출하도록 했다. 분석을 다시 실행하지 않았다.

| 단계 (초) | 1회 | 2회 | 3회 | 중앙값 |
| --- | ---: | ---: | ---: | ---: |
| 첫 캐시 생성 및 HTML | 10.79 | 9.63 | 9.54 | 9.63 |
| 동일 HTML 반복 생성 | 0.25 | 0.22 | 0.26 | 0.25 |
| 기존 함수로 새 HTML 생성 | 9.31 | 8.83 | 8.88 | 8.88 |
| 캐시 clear 후 재생성 | 8.92 | 9.36 | 9.13 | 9.13 |

각 프로세스의 순서는 표와 같다. 최초 호출 효과를 통제한 교차 순서의 제품 전후 실험은 아니다. 첫 캐시 생성은 기존 렌더링 비용을 없애지 않으며, 이득은 동일 결과의 반복 저장에서 발생한다. 결과 패널 생성과 8개 PNG·HTML 삽입을 포함하지만 PDF/Word/HWPX 변환과 앱 기동은 포함하지 않는다.

## 검증

- 3개 프로세스 각각 첫 생성·반복·기존 함수의 새 생성·clear 후 생성의 HTML, 메시지 문구·클래스·호출 정보, 난수 상태가 `identical(..., num.eq=FALSE)`로 동일했다. PNG URI도 HTML 비교에 포함한다.
- 첫 생성의 실제 그림 렌더러 호출은 8회, 반복에서는 추가 0회, clear 뒤에는 추가 8회였다.
- 실제 ggplot2 전역 테마·글꼴 설정 및 R options 변경 시 무효화를 별도로 검증했다. 이 검사는 렌더러 대역을 사용했으며 그림의 시각적 설정 변경 검사는 아니다. 변경한 설정은 복원했다.
- 기존 후보의 결과·종류·색상·언어·크기·해상도 구분, 용량 제한, 경고·알 수 없는 메시지·오류·난수 변화 우회 검사도 다시 통과했다.
