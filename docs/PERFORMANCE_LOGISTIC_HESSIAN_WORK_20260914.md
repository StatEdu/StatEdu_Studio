# 다항 로지스틱 Hessian 작업 행렬 축소 검토 — 2026-09-14

## 판단

운영 코드는 변경하지 않았다. 참조 범주 열을 만들었다가 삭제하는 작업을 생략하면 수치 결과는 유지되었지만, 초기 컴파일까지 고려한 통합 후보의 전체 분석 중앙값 감소는 약 3~4%이고 세 번째 쌍은 느려졌다. 이득의 일관성이 부족하고 nnet 내부 구현의 변환·호환성 관리가 필요해 이번 후보는 채택하지 않는다.

## 후보

설치된 nnet 7.3-20의 `multinomHess()`를 기준으로 했다. 기존 함수는 각 행·범주마다 p × (k+1) 영행렬에 해당 범주의 자료를 대입하고 첫 열을 제거한다. 후보는 p × k 영행렬로 시작하고 참조 범주는 대입을 생략하며 나머지 범주는 j-1열에 대입한다. `xbar`, 중심화, `crossprod`, 가중치·확률 곱셈 및 `info` 누적 순서는 유지한다.

첫 후보는 실험 환경에서 summary에 Hessian을 미리 제공하는 방식으로 연결했다. 새 함수의 첫 실행 컴파일 비용 때문에 이미 컴파일된 패키지 함수와 초기 비용이 달랐다. 명목형 다항에서는 중앙값 3.28→2.94초였지만 먼저 실행되는 순서형 입력의 자동 전환 경로는 4.02→4.16초로 느려졌다. 이를 전반적인 10% 개선으로 제시하지 않는다.

통합 후보 `current.R`은 계수 표 생성 시 Hessian이 없으면 보조 함수를 통해 계산한다. 보조 함수는 최초 사용 시 설치된 함수 복사본의 세 문장을 확인·변경하고 컴파일한다. 버전이나 예상 문장이 다르면 원래 구현을 사용하도록 했다. 패키지 네임스페이스는 수정하지 않는다. 기존 Hessian이 있으면 재계산하지 않는다. 이 방식 자체가 추가 호환성 관리 부담이다.

## 최종 통합 후보 시간

5만 행, 연속 예측변수 6개를 2개씩 추가한 3단계 전체 분석이다. 새 프로세스에서 기준/후보 각각 3회 순차 측정했고 두 번째 세트는 후보부터 실행했다. 각 조건 전에 동일 종류 360행 자료로 준비 실행했다. 입력 생성·부트스트랩·소스 로딩·사전 GC는 제외했으며 분석, 진단 수집, 비교용 공식 환경 정규화와 해당 시점에 발생하는 보조 함수 초기화는 포함했다. 화면 렌더링은 제외한다.

| 자료와 실제 경로 | 기준 3회(초) | 후보 3회(초) | 중앙값(초) |
|---|---|---|---|
| 이항 → 이항 | 1.18 / 1.20 / 1.20 | 1.22 / 1.18 / 1.28 | 1.20 → 1.22 |
| 순서형 → 다항 자동 전환 | 4.01 / 4.02 / 4.03 | 3.84 / 3.89 / 4.02 | 4.02 → 3.89 |
| 명목형 → 다항 | 3.27 / 3.28 / 3.26 | 3.11 / 3.13 / 3.39 | 3.27 → 3.13 |

순서형 입력은 기존 평행선 검정에 따라 다항으로 전환되는 자료다. 순수 순서형 적합 시간으로 해석하지 않는다. 마지막 후보 프로세스에서는 변경 경로를 사용하지 않는 이항도 느렸으므로 프로세스 간 변동 가능성이 있다. 이 자료로 통계적 유의성이나 일관된 개선/회귀를 단정하지 않는다. 후보의 이항 중앙값 변화는 Hessian 최적화의 직접 효과로 해석하지 않는다.

## 검증

- 초기 후보와 최종 통합 후보 각각 전체 분석 18조건 일치: 이항·순서형·명목형 × 일반·결측·범주형 예측변수·상수·중복열·반올림 예측변수. 검증 스크립트의 전체 분석 사례명 `weights`는 반올림 입력을 뜻하며 가중 분석이 아니다.
- 각각 Hessian 직접 비교 18조건 일치: 반응 범주 2/3/5개 × 예측변수 0/1/6개 × 단위/0·1·2 가중치. 최종 검증은 통합 보조 함수를 직접 호출했고, 원래 함수와 본문이 달라 실제 특화 경로가 활성화되었는지도 확인했다.
- 초기 및 최종 실측 결과 각각 9쌍의 전체 반환값·진단·표준출력·난수 상태가 일치했다. `identical(..., num.eq=FALSE)`를 사용했으며 공식 환경만 `.GlobalEnv`로 정규화했다. 수치 허용오차는 사용하지 않았다.
- 최초 직접 검증 스크립트가 행렬에 `$error`를 조회하는 오류는 행렬 검사로 수정하고 다시 실행했다.
- 최초 통합 버전 확인은 패키지 버전의 표시 형식 `7.3-20`과 `packageVersion()`의 정규화된 문자 `7.3.20` 차이로 원래 함수를 선택했다. 그 실행은 `integration-guard-fallback/`에 별도 보관했으며 최종 성능 근거에서 제외했다. 표기 수정 및 활성 경로 검사 후 최종 3세트를 새로 측정했다.

모든 가능한 입력, 다른 nnet 버전의 대체 경로, 실제 앱 전체 실행을 검증한 것은 아니다. 최고 메모리와 프로그램 로딩 시간은 측정하지 않았다.

## 파일 및 적용 상태

자료는 `output/logistic-hessian-work-20260914/`에 있다. `baseline.R`은 운영 소스이며 `hessian.R`은 초기 후보, `engine.R`과 `current.R`은 미적용 통합 후보다. `common.R`/`verify.R`/`measure.R`/`compare.R`은 초기 실험, 이름에 `_integration`이 붙은 스크립트는 최종 후보 실험이다. 최종 시간 및 RDS는 `integration/`에 보관했다.

운영 `R/analysis_logistic.R`과 기준 사본이 동일함을 확인했다. 준비해 둔 `presentation.R`과 `exports.R`은 실행하지 않았으며 내보내기를 검증했다고 주장하지 않는다. 후보를 채택하지 않아 출력과 설치 파일도 변경하지 않았다.
