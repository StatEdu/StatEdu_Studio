# 카운트 GLM 단계별 비용과 로딩 오류 수정 — 2026-09-14

카운트 모형의 주된 비용은 모형 적합 단계였다. Poisson이 선택되더라도 음이항 모형의 AIC/BIC/logLik 비교를 결과표에 제공하므로 음이항 적합을 생략하면 현재 결과 내용이 달라진다. 이번에는 수치 분석 코드를 변경하지 않았다.

## 단계별 시간

50,000행과 연속 예측변수 6개를 사용했다. Poisson 자료 및 과산포 자료를 시드 915로 생성했고 실제 반환 모형을 확인했다. 후자는 음이항 분포 size=0.5를 사용했다.

| 자료 / 실제 선택 모형 | 전체 3회(초) | 전체 중앙값 | 적합 단계 중앙값 | 계수 표 중앙값 | 가정 점검 중앙값 |
|---|---|---:|---:|---:|---:|
| Poisson / Poisson | 1.20 / 1.13 / 1.32 | 1.20 | 1.00 | 0.07 | 0.02 |
| 과산포 / 음이항 | 1.11 / 1.18 / 1.22 | 1.18 | 0.92 | 0.07 | 0.05 |

계수 표는 적합 단계의 하위 호출이므로 두 시간을 더하면 안 된다. 여기서 적합 단계는 Poisson·음이항 적합, 비교 지표·계수 표 생성 등을 함께 포함한다. 두 패키지 적합 함수의 개별 시간은 분리하지 않았다. 전처리와 적합도 표는 대부분 0.00~0.02초였으며 0.00은 비용이 없다는 뜻이 아니다.

번들 R 4.5.3의 새 프로세스 3개를 순차 실행했다. 각 조건을 준비 실행 후 GC와 함께 측정했다. 강건 표준오차·가정 점검 켬, VIF 끔, 완전 자료이다. 계측 래퍼는 인수를 미리 강제 평가하지 않는다. 입력 생성·모듈 로딩·화면·저장은 제외하고 결과 준비·스냅샷 구성·조건 수집을 포함한다. 다른 R 작업은 동시에 실행하지 않았다. 메모리는 측정하지 않았다.

준비/측정 및 프로세스 간 비교에서 스냅샷이 정확히 일치했다. 반환 결과에서 원래 모형 객체를 제외한 내용, 별도 계수·적합값·잔차·deviance·weights, 경고/메시지 문자열·난수 상태를 `identical(..., num.eq=FALSE)`로 비교했다. 공식 환경만 `.GlobalEnv`로 통일했으며 모형 내부 클로저 등 모든 필드의 동일성을 주장하지 않는다. 이는 현행 결과의 재현성 확인이며 새로운 최적화의 개선율 측정이 아니다.

## 함께 발견한 로딩 오류

최초 측정은 `R/analysis_scope.R`의 `analysis_scope_panel()` 스타일 정의 뒤에 닫는 괄호가 하나 많아 중단됐다. 합친 모듈 캐시 로딩과 개별 파일 로딩 모두 구문 오류로 실패했다. 해당 위치의 괄호 하나만 제거하고 다음을 확인했다.

- `parse("R/analysis_scope.R")` 통과
- 앱 모듈 로딩 후 카운트 분석의 새 프로세스 3회 측정 완료
- `scripts/validate_analysis_scope_startup.R` 통과: 전체 앱 서버와 케이스 선택·파일 분할의 두 지연 로딩 패널 초기화 확인

기존 스타일 문자열이나 화면 설계, 분석 범위 규칙은 변경하지 않았다. 초기 구문 오류로 중단된 실행은 시간 표에 포함하지 않았다. 이번 운영 수정은 이 문법 오류 한 곳이며 수치 모형 적합 생략은 적용하지 않았다.

측정 코드·CSV·결과 RDS·교차 비교 코드는 `output/glm-count-stages-20260914/`에 보관했다. 출력 내용·형식은 변경하지 않았고 PDF/Word/HWPX/Excel 전체 변환 및 설치 파일 재빌드는 수행하지 않았다.
