# Gwet 가중치 조회의 평가자 위치 재사용 검토

## 결론

평가자 쌍의 좌우 위치 벡터를 유효 평가자 수가 바뀔 때만 꺼내고, 각 행에서 그 위치의 범주 코드로 가중치를 조회하는 후보를 시험했다. 원시 계수 비교는 통과했지만 순서형 전체 분석이 세 번 중 두 번 느려져 적용하지 않았다. 기존 제품 코드는 유지했다.

## 후보

기존에는 매 행마다 `matrix(values[pair_indices], nrow=2L)`를 생성하고 다시 두 행을 꺼내 cbind로 가중치 행렬의 인덱스를 만들었다. 후보는 pair_indices가 갱신될 때 pair_left/pair_right를 저장하고, 각 행에서 `cbind(values[pair_left], values[pair_right])`로 바로 조회한다. 분모는 동일한 쌍 수인 ncol(pair_indices)를 사용한다.

범주 값 자체나 가중치 조회 결과를 캐시한 것은 아니다. 범주 매칭, 결측 제거, 기존 크기별 쌍 캐시, 가중치 행렬, 쌍 순서와 합산 순서는 유지했다. 이전에 보류한 일괄 범주 매칭 후보는 포함하지 않았다.

## 전체 분석 성능

번들 R 4.5.3, seed 939, 20,000행·8평가자, A–E와 NA를 같은 확률로 표집한 자료다. 명목형/순서형의 전체 prepare_interrater_agreement_results를 비교했다. 독립 프로세스 3개를 순차 실행했고 워밍업 후 두 번째는 후보를 먼저 측정했다. 로딩을 제외하고 전체 결과 캡처를 포함한다.

| 유형 | 현재 1 / 2 / 3 (초) | 후보 1 / 2 / 3 (초) | 중앙값 |
|---|---|---|---|
| 명목형 | 0.41 / 0.39 / 0.39 | 0.39 / 0.38 / 0.38 | 0.39 → 0.38 |
| 순서형 | 0.28 / 0.38 / 0.27 | 0.36 / 0.25 / 0.34 | 0.28 → 0.34 |

명목형은 세 번 모두 소폭 빨라졌지만 순서형은 두 번 느려졌다. 공통 경로에 적용할 만큼 일관된 이득으로 판단하지 않았다. 측정 편차의 내부 원인이나 모든 자료의 실행 시간을 단정하지 않는다.

## 검증

변경 직전 실제 소스를 참조로 192개 원시 Gwet 계수·조건·RNG 비교를 수행해 통과했다. 평가자 수 1/2/3/10/30/32/33/40, 완전·결측·희소·미등록 값·빈·factor 자료와 AC1/AC2, linear/quadratic 조합을 포함한다.

전체 분석의 워밍업과 측정 각각에서 전체 반환 객체, 조건 클래스·본문·순서, 표준 출력 및 RNG가 `identical(..., num.eq=FALSE)`로 일치했다. 수치 허용오차나 정규화는 사용하지 않았다. 개별 쌍의 가중치 벡터를 별도로 수집한 검증은 아니다.

시험용 validate.R은 기존 검증 스크립트가 후보를 로드하도록 복사한 것이며, 반드시 비교 기준 소스 인자를 전달한 실행을 사용했다. 해당 복사본의 인수 없는 참조 변환은 새 후보용 독립 검증으로 주장하지 않는다.

## 증거와 범위

`output/gwet-weight-index-review-20260914/`에 baseline.R, candidate.R, bench.R, timing-1/2/3.csv, 실행 로그 및 validate.R/validation.log를 보관했다. 제품과 시작 스냅샷의 해시가 같은지 확인했다.

메모리 최고 사용량은 측정하지 않았다. 제품·출력 변경이 없어 전체 형식 변환, 설치 파일 빌드 및 종합 일치도 검증은 재실행하지 않았다.
