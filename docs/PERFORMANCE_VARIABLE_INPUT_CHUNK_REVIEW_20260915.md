# 변수 설정 공통 입력 수집의 분할 조회 검토

2026-09-15. 변수 라벨과 측정수준 수집에서 함께 사용하는 `collect_variable_input_values()`에 64행 단위 격리 조회를 적용하는 연구 후보를 비교했다. 제품에는 적용하지 않았다. 기존 범주 라벨 적용 버튼 전용 분할 조회는 유지한다.

## 호출 범위와 반응성

공통 입력 수집은 `create_table_input_collectors()`를 거쳐 변수 정보 상태 병합 및 설정 스냅샷 경로에도 연결된다. 기존 함수는 호출자의 반응성 컨텍스트에 입력 의존성을 등록한다. 연구 후보는 내부 `isolate()`에서 값을 읽으므로 일반 반응형 호출에서 이 계약이 달라진다.

Shiny `testServer()` 안에서 실제 수집 함수를 observer가 호출하도록 구성하고 입력을 `first`에서 `second`로 변경했다. 기존 함수는 두 번 실행되어 변경된 값을 수집했지만 연구 후보는 한 번만 실행되어 첫 값을 유지했다. 독립 프로세스 두 번 모두 재현했다. 이는 연구 후보의 문제이며 제품에 이미 적용된 오류라는 뜻은 아니다.

범주 라벨 적용 버튼은 이벤트 핸들러가 이미 격리된 조회를 하므로 별도 이벤트용 함수를 두었다. 이 전용 개선을 일반 수집 함수 전체로 확대하면 안 된다는 것을 확인했다.

## 성능

`scripts/review_variable_input_chunks.R`에서 일반 변수 라벨 입력만 있는 경우와 보조 범주 라벨 입력만 있는 경우를 비교했다. 기존 함수는 앞 입력 접두사부터 조회하고 첫 번째 NULL 아닌 값을 사용한다. 보조 입력만 있으면 각 변수마다 두 키를 읽는다.

독립 R 프로세스 2개에서 순서를 뒤집어 측정했다. 동일한 Shiny 입력 객체를 사전 호출하고 함수의 최상위 코드를 컴파일했다. 명시적인 GC와 입력 준비를 제외한 isolate 내 수집 호출을 `Sys.time()`으로 한 번씩 측정했다. 사전/측정 반환 벡터와 이름은 `identical(..., num.eq=FALSE)`로 일치했다. 진단·RNG 전체 또는 모든 비정상 입력의 동등성을 입증하는 검사는 아니다.

| 변수 수 / 입력 위치 | 실행 | 기존 초 | 후보 초 |
|---|---:|---:|---:|
| 1,000 / 일반 | 1 | 0.136450 | 0.146199 |
| 1,000 / 일반 | 2 | 0.134504 | 0.141508 |
| 1,000 / 보조 | 1 | 0.224007 | 0.296007 |
| 1,000 / 보조 | 2 | 0.241020 | 0.221376 |
| 5,000 / 일반 | 1 | 1.253132 | 1.137290 |
| 5,000 / 일반 | 2 | 1.305565 | 1.154448 |
| 5,000 / 보조 | 1 | 2.554704 | 1.736563 |
| 5,000 / 보조 | 2 | 2.522741 | 1.815470 |

5,000변수의 보조 입력 조건에서는 약 28~32% 단축됐지만, 1,000변수 조건은 일부 느려졌다. 반응성 계약까지 달라지므로 일반 함수에 채택하지 않는다. 이 수치는 입력 수집 구간이며 전체 설정 저장, 브라우저, 파일 쓰기 또는 분석 계산 시간은 아니다.

후속 작업은 별도 이벤트 경로에서 실제 규모와 병목이 확인될 때만 검토한다. 공통 수집 함수의 입력 의존성 등록을 일괄 제거하지 않는다.
